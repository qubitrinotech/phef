## 3. Закон роста времени до escape

Данные при `batch_size=256, dim=128`:

| seg | escape_epoch | множитель |
|------|--------------|-----------|
| 2048 | 2750–3250 | — |
| 4096 | 4750–6000 | ~1.8 |
| 8192 | 9250 | ~1.7 |
| 16384 | **22500** | ~2.4 |

Средний множитель 1.9–2.0 на удвоение сегментов. Именно поэтому барьер выглядел непреодолимым: прогоны при batch 64 на 50k эпох не доходили до нужной точки, а при batch 256 на 16384 их до 18 августа никто не запускал.

Экстраполяция (при 124 эп/мин): 32768 → ~45000 эпох (~6 ч до escape), 65536 → ~90000 (~12 ч), 1M → миллионы эпох (месяцы).

**Отсюда новая задача проекта: сократить время до escape.** Без этого перебор гипотез на больших масштабах невозможен.

## 4. Что опровергнуто из хендоффов №10 и №11

Все перечисленные формулировки построены на серии с `batch_size=64` и недействительны:

- «Жёсткий предел — 8192 сегмента для dim=32/64/128» — опровергнуто, 16384 работает.
- «При 16384 сегментах все размерности полностью деградируют до случайного угадывания» — фактически 1.4–1.9 chance (0.0229–0.0293 против 0.015625), застряло под порогом 0.03125, а не «случайное угадывание».
- «Узкое место не в dim, key_dim, n_keys» — формально верно, но вывод «узкое место не найдено» неверен: оно было в `batch_size`, который не рассматривался как переменная.
- «dim=256 не расширяет ёмкость, на 8192 уже проваливается» — **под подозрением**: серия dim=256/seg=8192 (0.0145/0.0137/0.0180) шла при `--batch-size 64` по `run_capacity.sh`. Требует перепрогона.
- «✅ 0.999+ у всех трёх сидов» для dim=128/8192 — неверно: в файлах были только s0 и s2, сида 1 не существовало. Прогон s1 при batch 64 провалился (`best 0.0205 @ 2750`).
- Эксперимент D этой сессии (`--select-metric hard`, 2 сида × 100k, 13 часов) шёл при batch 64 и потому ничего не проверял. Его отрицательный результат **аннулирован**.

## 7. ПРИОРИТЕТ 2: ускорение обучения

Новая главная задача. Ниже — только обоснованные варианты, с указанием того, что уже проверено и что ещё нет.

### 7.1. Curriculum learning — предпосылка ПОДТВЕРЖДЕНА

Структуры чекпоинтов при seg=8192 и seg=16384 **идентичны**, 16 тензоров:

```
recency_scale ()          score_scale ()          memory_gate ()
key_encoder.0.weight (128, 32)     key_encoder.0.bias (128,)
key_encoder.2.weight (128, 128)    key_encoder.2.bias (128,)
query_encoder.0.weight (128, 32)   query_encoder.0.bias (128,)
query_encoder.2.weight (128, 128)  query_encoder.2.bias (128,)
value_emb.weight (64, 128)         norm.weight (128,)  norm.bias (128,)
head.weight (64, 128)              head.bias (64,)
```

**Ни один параметр не зависит от `n_segments`.** Сегменты входят только как данные. Значит веса, обученные на 8192, грузятся в модель на 16384 без переформатирования.

Гипотеза: escape на 16384 наступит существенно раньше 22500, если стартовать с весов, обученных на 8192 (где escape был на 9250).

**Блокер:** в `analyze_memory.py` (693 строки, 22 аргумента argparse) **нет флага загрузки начальных весов**. Требуется правка кода: добавить `--init-weights PATH` с `model.load_state_dict(torch.load(path))` после создания модели. Перед правкой обязательно прочитать `cat -n experiments/analyze_memory.py` в районе создания модели и оптимизатора (по хендоффу №8 это строки 425–434) — не править вслепую.

Оценка выигрыша: неизвестна. Ожидание 2–3x основано на аналогии, не на данных.

### 7.2. Инициализация score_scale — ОБОСНОВАНА, но формула не выведена

Факт: модель стартует с `score_scale=1.0` (инициализация в `model.py`, строки 37–39) и приходит к **4.83** при 16384 сегментах. Из истории s0: на эпохе 250 значение 1.0168, то есть первые тысячи эпох уходят на подъём.

Предложение `score_scale = log(n_segments) ≈ 9.7` для 16384 **вдвое превышает выученное значение**. Инициализация выше оптимума может замедлить сходимость, а не ускорить.

Нужна зависимость `score_scale` от `n_segments` по успешным прогонам при 2048, 4096, 8192, 16384. Попытка собрать её упала с `KeyError: 'history'` — в части старых JSON этого ключа нет. Исправленная команда:

```bash
cd ~/qubitrino-projects/agi/phef
python3 -c "
import json,glob,math
rows=[]
for p in sorted(glob.glob('results/**/dim*_seg*_s*_e*.json',recursive=True)):
    r=json.load(open(p)); c=r.get('config',{})
    if r.get('answer_acc',0)>0.9 and c.get('dim')==128:
        ss=r.get('score_scale'); rs=r.get('recency_scale'); mg=r.get('memory_gate')
        h=r.get('history')
        if h and isinstance(h,list) and h:
            ss=h[-1].get('score_scale',ss); rs=h[-1].get('recency_scale',rs); mg=h[-1].get('memory_gate',mg)
        rows.append((c.get('n_segments'),c.get('batch_size'),c.get('seed'),
                     r.get('escape_epoch'),ss,rs,mg,'history' if h else 'top-level'))
rows.sort(key=lambda x:(x[0] or 0,x[2] or 0))
print(f\"{'seg':>6} {'batch':>6} {'s':>2} {'escape':>7} {'ss':>9} {'rs':>9} {'mg':>9}  src\")
for seg,b,s,e,ss,rs,mg,src in rows:
    f=lambda v: f'{v:9.3f}' if isinstance(v,(int,float)) else f'{str(v):>9}'
    print(f'{seg:6} {b:6} {s:2} {str(e):>7} {f(ss)} {f(rs)} {f(mg)}  {src}')
"
```

Если `score_scale` растёт как `log2(seg)` или `sqrt(seg)` — формула инициализации выводится из данных. Это бесплатно, минуты работы, и должно быть сделано до правки кода.

### 7.3. Gradient accumulation — нужен позже, не сейчас

Накопление градиентов даст эффективный батч 256 при памяти как у 64. Но при seg=16384 batch 256 занимает **11819 MiB из 24564** — проблемы памяти на этом масштабе нет.

Понадобится на seg=32768 и выше, где batch 256 может не влезть. Тогда и реализовывать.

### 7.4. Что НЕ делать: инициализация recency_scale = 0.1

Предложение опирается на хендофф 8.1, где `--recency-value 0.1` давал прирост. Но там были `dim=8, seg≤1024`. Успешный прогон на 16384 выучил `recency_scale = 32.7`. Инициализация значением 0.1 — это 0.3% пути к выученному значению, то есть практически то же, что старт с нуля.

### 7.5. InfoNCE / auxiliary retrieval loss — требует чтения кода

Идея: добавить `retrieval_loss = cross_entropy(scores, answer_positions)` к основному лоссу.

Предпосылка проверяема: в хендоффе №9 зафиксировано, что при `retrieval_loss=0` (прямой надзор) точность 0.999 держалась на 256 сегментах. Но структура функции потерь в текущем коде **не читалась в этой сессии**. Перед реализацией: `cat -n experiments/analyze_memory.py` в районе вычисления лосса и шага оптимизатора.

Также учесть: `--select-metric hard` уже проверен на 16384 при batch 64 и не помог — но тот прогон недействителен из-за батча. Повтор при batch 256 может дать другой результат и стоит дешевле, чем правка кода (флаг уже существует).

### 7.6. Двухступенчатый retrieval — самый большой потенциал, самая большая цена

Идея: кластеризовать 16384 ключа в ~128 групп, искать сначала кластер, потом ключ внутри. Сложность O(n) → O(√n).

В проекте уже есть `experiments/probe_two_stage.py` (424 строки по хендоффу №8) и результаты `results/v5/two_stage.json`. Начинать надо с чтения этого скрипта, а не с новой реализации.

### 7.7. Новые варианты, не предлагавшиеся ранее

**А. Проверить, нужны ли 50k эпох вообще.** Escape на 22500, точность 0.9731 к 42750, 0.9998 к 50000. Возможно, `--epochs 30000` достаточно для 0.99+. Это бесплатное ускорение всех будущих прогонов на 40%. Проверка: прочитать `history` из готового JSON s0 и найти эпоху, где точность впервые превысила 0.99.

**Б. lr выше при большом батче.** При batch 256 градиент в 4 раза менее шумный, чем при 64, а `lr=1e-3` остался прежним. Классическое правило масштабирования (linear scaling rule) предполагает рост lr вместе с батчем. Проверка дешёвая: 1 прогон при `--lr 2e-3` или `--lr 4e-3`, seg=16384, 40k эпох. Если escape сместится с 22500 к 12000–15000 — это ускорение в 1.5–2x одним флагом, без правки кода. **Флаг уже существует, кода менять не нужно** — самый дешёвый из всех вариантов ускорения.

**В. `--lr-decay`** существует как флаг и ни разу не использовался ни в одном из 22 прогонов (`lr_decay = False` во всех config). Влияние неизвестно.

**Д. Восстановить упавший smoke на batch 256.** Дважды упал на финальной оценке из-за `eval_batch_size=512`. Нужен для получения `raw_top1` и `score_top1` на коротком прогоне — полезно как быстрый тест конфигураций. Повтор с `--eval-batch-size 128` займёт минуты.

## 8. ПРИОРИТЕТ 3: перепроверка старых выводов при batch 256

Все эти прогоны проверяют утверждения хендоффов №10/№11, полученные при batch 64:

1. **dim=256, seg=8192, batch 256, 3 сида** — был ли провал dim=256 артефактом батча.
2. **dim=32 и dim=64, seg=16384, batch 256** — работают ли малые dim на 16384 (при batch 64 провалились все).
3. **seg=32768, batch 256** — новый рубеж. Escape ожидается около 45000 эпох, значит нужно минимум 60k. Прогоны на 32768 (dim=128, 3 сида, 150k эпох) и 65536 (dim=256, 3 сида) уже запускались 11 августа и упали с OOM — но по traceback видно, что причина в параллельном запуске трёх сидов, а не в размере задачи: сам прогон dim=256/seg=65536 занимал 7.37 ГБ из 23.52, а падение произошло при суммарной занятости 22.06 ГБ тремя процессами. Флаг expandable_segments:True тогда не применялся. Вывод: запускать по одному сиду последовательно, с флагом — 32768 и, вероятно, 65536 достижимы без gradient accumulation. Логи: logs/capacity_scan_dim128_extended/dim128_seg32768_s*_e150000.log (196 байт, смерть на инициализации), logs/capacity_scan_dim256/dim256_seg65536_s*_e100k.log, logs/capacity_scan_dim256/dim256_seg32768_s*_e100k.log, logs/capacity_scan_dim256_1M/ (294 байта каждый). 
4. **key_dim=64 и n_keys=1024 при batch 256** — их «провал» из хендоффа №11 недействителен, эффект неизвестен.

## 9. Главные правила для нового агента

- **НЕ ГАДАТЬ. НЕ ФАНТАЗИРОВАТЬ.** Опираться только на факты, полученные в текущей сессии.
- **Всегда сверять `config` из целевого JSON**, а не брать параметры из текста хендоффа. Именно эта ошибка (взял `batch-size 64` из хендоффа №10 вместо `config` файла) стоила проекту недели — но она же и вскрыла настоящую причину.
- **Не экстраполировать между конфигурациями.** OOM при dim=256 не означает OOM при dim=128. Escape на 9250 при 8192 не означает escape к 20500 при 16384 — реальное значение 22500, и преждевременный вывод «гипотеза не подтверждается» был сделан за 2000 эпох до прорыва.
- **Не судить о провале до расчётной эпохи escape.** Ожидаемая точка = escape(seg/2) × 2.4. Для 32768 это около 45000 эпох.
- Проверять состояние через `ps -o pid,etime,cmd -C python | grep analyze_memory`, `nvidia-smi`, `ls -la`, `tail`, `date`.
- **Всегда `nohup ... > файл.log 2>&1 &`**, никогда `| tail -N`: пайп буферизует весь вывод до завершения процесса, прогресс не виден, а при закрытии терминала теряется целиком.
- `grep` без совпадений возвращает код 1 — это норма, а не ошибка.
- JSON и `.pt` пишутся **только в конце прогона**. Прерывание или перезагрузка = полная потеря результата. Промежуточных чекпоинтов нет.
- Прогон детерминирован: `make_world(seed)` для train, `seed+100000` для eval, `seed+200000` для sel. Перезапуск даёт ту же траекторию.
- Перед правкой кода — читать `cat -n`. Не ссылаться на строки, которые не читал.
