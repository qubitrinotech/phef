## 3. Правка кода: флаг `--init-weights`

**[ФАКТ]** Внесена, закоммичена в `079ccae`, проверена через `--help`. Файл вырос с 693 до 702 строк (9 вставок, 0 удалений — по `git diff --stat`).

Вставка 1, после строки 382 (`--out`), перед многострочным `--world` на 383:

```python
    parser.add_argument("--init-weights", type=str, default=None)
```

Вставка 2, в пустую строку 440 — между `.to(device)` на 439 и `if args.freeze_recency` на 441:

```python
    if args.init_weights is not None:
        ckpt = torch.load(args.init_weights, map_location=device)
        sd = ckpt["state_dict"] if "state_dict" in ckpt else ckpt
        model.load_state_dict(sd, strict=True)
        print(f"init_weights loaded from {args.init_weights} "
              f"src n_segments={ckpt.get('config',{}).get('n_segments')} "
              f"src escape={ckpt.get('escape_epoch')}", flush=True)
```

Порядок вставки 2 обязателен, обоснование из прочитанного кода:

- **после** `.to(device)` (439) — иначе тензоры чекпоинта окажутся на другом устройстве;
- **до** блока 441–449 — там `freeze_recency` делает `recency_scale.zero_()`, а `recency_value` делает `fill_()`; загрузка после них перезаписала бы установленное значение и сломала семантику обоих флагов;
- **до** `AdamW` на 451 — он фильтрует параметры по `requires_grad`, список должен формироваться после всех манипуляций с моделью.

**[ФАКТ]** Формат `.pt`: `dict` с шестью ключами — `state_dict`, `config`, `best_epoch`, `best_acc`, `selection`, `escape_epoch`. Прочитано через `torch.load(..., map_location='cpu')`. Ключ именно `state_dict`, не `model`.

**[ФАКТ]** `strict=True` безопасен. Проверено сравнением двух чекпоинтов (8192 и 16384): `keys equal: True`, `shape diffs: []`, по 16 тензоров в каждом. Ни один параметр не зависит от `n_segments`.

Контрольная печать `init_weights loaded ... src n_segments=... src escape=...` — не косметика. Она читает `config` из самого `.pt`, поэтому источник весов видно в логе, и не приходится доверять имени файла.

## 4. Что закрыто отрицательно

### 4.1. [ЗАКРЫТО] 7.7.Б — повышение lr

Гипотеза: linear scaling rule, при batch 256 нужен lr выше 1e-3.

Прогон: сид 1, `--lr 2e-3`, seg 16384, 40k эпох. Отличие от провалившегося прогона того же сида — **только lr**, сверено по `config`.

Результат: `answer_acc 0.0168`, `retrieval_acc 0.00234`, `escape None`, `max sel_acc 0.0229`.

Финальные масштабы: `score_scale 0.0089`, `recency_scale 0.724`, `memory_gate 0.1833`. При старте с нуля `score_scale = 1.0`, то есть **удвоенный lr загнал параметр в 112 раз ниже стартового значения**.

Траектория `memory_gate` показывает разворот: 0.314 на 6250 → 0.430 на 12000 → **0.271** на 22500. Параметр рос и пошёл вниз. У успешного s3 в тех же точках: 0.324 → 0.535 → **2.895**.

Вывод: больший lr не ускоряет выход из плато, а закрепляет вырожденное решение с выключенной памятью. `--lr 4e-3` проверять бессмысленно — направление видно.

### 4.2. [ЗАКРЫТО] 7.2 — инициализация score_scale по формуле

Хендофф №12 предлагал `score_scale = log(n_segments)`, то есть ≈9.7 для 16384.

**[ФАКТ]** Фактические выученные значения `score_scale` при curriculum: 5.989 (16384, s0), 6.415 (16384, s1), 5.565 (32768, s0). Формула завышает примерно вдвое.

Отдельно снят вопрос немонотонности. У прогонов с нуля наблюдалось падение: 6.26–6.43 при 8192 → 4.008–4.977 при 16384 (три точки: s0 4.977, s2 4.376, s3 4.008). Это оказалось **признаком недообученности**, а не свойством оптимума: curriculum-прогоны на тех же 16384 дали 5.99 и 6.41, то есть вернулись на уровень 8192.

`score_scale` от размера почти не зависит — держится в диапазоне 5.6–6.4 на всех рубежах при достаточном обучении.

### 4.3. [ЗАКРЫТО] 7.7.А — сокращение эпох до 30k

## 13. Правила для нового агента

Правила из №12 действуют полностью. Ниже — с уточнениями, которые сессия 19–20 августа подтвердила на практике.

**НЕ ГАДАТЬ. НЕ ФАНТАЗИРОВАТЬ.** Опираться только на факты текущей сессии. Конкретно это означает:

- **Не догадываться о содержимом функции.** Если нужно знать, что делает функция или как устроен блок кода — прочитать `cat -n файл | sed -n 'A,Bp'` и только потом говорить о нём. В этой сессии перед правкой были прочитаны строки 378–390 и 432–445; ошибка в порядке вставки (загрузка весов после `freeze_recency`) сломала бы флаги `--freeze-recency` и `--recency-value`, и обнаружилась бы только по странным результатам через 8 часов.
- **Не догадываться о формате файла.** Формат `.pt` был проверен `torch.load` перед написанием кода загрузки. Первоначальное предположение о ключе `model` оказалось неверным — реальный ключ `state_dict`. Догадка стоила бы падения прогона.
- **Не догадываться о номерах строк.** Хендофф №8 указывал «строки 425–434» для создания модели; фактически 432–439. Расхождение небольшое, но вставка по памяти попала бы не туда.
- **Не догадываться о совместимости.** Перед curriculum было проверено сравнение двух `state_dict`: `keys equal: True`, `shape diffs: []`. Только после этого `strict=True` был признан безопасным.
- **Не принимать вывод команды на веру, если он неоднозначен.** В этой сессии `grep ... | head -1` по двум логам дал вывод, из которого нельзя было определить, какому сиду принадлежит строка `escape 23500`. Вместо предположения был запрошен разделённый вывод с `echo "=== s$s ==="`. Первоначальная атрибуция оказалась неверной.
- **Не объяснять расхождение, не проверив.** Файл вырос на 9 строк вместо ожидаемых 8. Причина выяснилась через `git diff` (лишняя пустая строка), а не через рассуждение.

**Всегда сверять `config` из целевого JSON**, а не брать параметры из текста хендоффа. В этой сессии сверка выполнялась перед каждым выводом: у прогона `lr2e3` подтверждено `lr: 0.002`, у остальных `lr: 0.001`. Без этого сравнение было бы бессмысленным.

**Не экстраполировать между конфигурациями.** Память при 32768 (16699 MiB) не выводится из памяти при 16384 (11819 MiB) — прирост оказался 4.9 GiB, а не удвоение. Для 65536 замерять, а не считать.

**Не судить о провале до расчётной эпохи escape.** Формула: escape(предыдущий рубеж) × 2.4. Для обучения с нуля на 32768 это ≈54000 эпох. Для curriculum от 32768 — 250 × 2.4 = 600 эпох. Пример из этой сессии: s0 на эпохе 22250 показывал `sel_acc 0.0112` и выглядел мёртвым, а на 22500 дал 0.5605.

**Всегда `nohup ... > файл.log 2>&1 &`**, никогда `| tail`. Пайп буферизует вывод до завершения процесса.

**Проверять состояние через** `ps -o pid,etime,cmd -C python | grep analyze_memory`, `nvidia-smi`, `ls -la`, `tail`, `date`. `grep` без совпадений возвращает код 1 — это норма.

**JSON и `.pt` пишутся только в конце прогона.** Промежуточных чекпоинтов нет. Прерывание = полная потеря результата.

**Масштабы (`score_scale`, `recency_scale`, `memory_gate`) в лог по ходу обучения не печатаются.** Проверено: `grep -cE "score_scale|memory_gate|recency_scale"` по логу даёт 3 совпадения на весь файл — только финальный блок. Ранняя диагностика по масштабам невозможна, читать из `history` в JSON после финала.

**Прогон детерминирован:** `make_world(seed)` для train, `seed+100000` для eval, `seed+200000` для sel. Перезапуск даёт ту же траекторию.

**Все команды выполняет пользователь.** Агент не имеет доступа к машине, запрашивает вывод и ничего не запускает без явного подтверждения.
