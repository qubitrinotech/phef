## 4. Что установлено (с указанием, чем именно)

1. **Ошибки при dim 8 — чисто адресационные, не декодирование.**
   `answer_acc` = `retrieval_acc` = `retrieval_value_acc` = `score_top1`
   с точностью до третьего знака во всех трёх сидах (0.7752 / 0.7714 / 0.7753
   для сида 0). Небольшой перевес `answer` над `retr` — коллизии значений
   при 256 значениях, ожидаемая частота.

2. **Разброс при dim 8 унаследован из геометрии ключей, а не из оптимизации
   ридаута.** `raw_top1` = 1.0 везде (в исходном key_dim 32 ключи различимы
   идеально), а `mg_top1` = 0.8084 / 0.9524 / 0.8602 гуляет на 0.144.
   Отставание факта от своего потолка узкое и стабильное: 0.033 / 0.023 / 0.031.

3. **Разложение ошибки меняет режим между dim 8 и dim 12.** Доля ошибок,
   объяснимая геометрическим потолком (`1 − mg_top1` от полной ошибки):
   85% / 68% / 82% при dim 8, 41% при dim 12, 36% при dim 16, 22% при dim 32.
   Ниже dim 12 узкое место — вместимость ключевого пространства
   (512 ключей в 8 измерениях), выше — скоринг и recency.

4. **Superposition реален и монотонен по dim.** `hard_soft_gap`
   +0.131 / +0.075 / +0.044 / +0.012 / +0.009 / +0.007 при dim 8 → 128.
   Контроль «hard-read == soft-read» из первого отчёта верен только при
   широком представлении. Следствие: таблица эмерджентности из раздела 5
   отчёта снята в soft-ридауте (`HARD_EVAL = False` в `train_recall.py`
   строка 14), а capacity-таблица — в hard. Две headline-таблицы отчёта
   в разных ридаутах и напрямую несопоставимы.

5. **Вывод «key_encoder уничтожает разделимость» — артефакт метрики.**
   Косинусные `enc_m0.05` в старом коде считались после `F.normalize`, тогда
   как модель скорит `dot/sqrt(dim)` без нормировки. В геометрии модели
   `mg_top1` = 0.9988 при dim 32. Абсолютный порог зазора 0.05 в
   ненормированной геометрии измеряет масштаб выходов энкодера, а не
   разделимость. Раздел 4.3 отчёта требует переписывания.

6. **Закон escape пересчитан на однородной серии:**
   `escape = 648 × (128/dim)^0.7815`, CI показателя 0.67–0.95, CI префактора
   451–745. Префактор 750 отвергнут (это было значение одной точки dim 128),
   независимый OLS из отчёта (646) подтверждён.
   Оговорка: `escape_epoch` квантован шагом `--acc-every 250`, при dim 128
   само значение 750, то есть ±33% на опорной точке. Остатки фита
   (1.157, 0.898, 0.870, 1.063, 0.930, 1.119) выглядят структурно, но с такой
   сеткой отличить систематику от квантования нельзя. Для точного префактора
   точки dim 64 и 128 надо перемерять с `--acc-every 50`.

7. **Ни одна точка кривой не сошлась.** Наклон `log(1 − sel_acc)` по
   `log(epoch)` на последней трети бюджета: −1.10…−1.22 при dim 12,
   −1.12…−1.41 при dim 16, −1.17…−2.04 при dim 32, −0.64…−1.28 при dim 8.
   Все растут. **Значит capacity-таблица измеряет положение траектории на
   фиксированной эпохе, а не вместимость памяти.** Термин «вместимость» из
   отчёта надо снять до выяснения.

8. **`tie_rate` бесполезен по построению** — при непрерывных ключах ничьих
   практически не бывает (`tie_rate_mean` 0.0000–0.0001).

9. **GPU-мир прошёл гейт сопоставимости.** dim 32, 12000 эпох, 3 сида:
   `answer_acc` 0.9982 против 0.9981 у numpy при sd 0.0005, `escape` дал то же
   множество {1500, 1750, 1750}, `mg_top1` 0.9994 против 0.9996.
   Побитовой совместимости нет и быть не может (`torch.Generator` вместо
   `numpy.Generator`), сверка только распределённая.

## 5. Что опровергнуто в ходе стадии

- «Отставание `answer` от `mg_top1` постоянно по всей кривой» — нет,
  абсолютное отставание падает с ростом dim (0.033 → 0.021 → 0.007 → 0.002),
  меняется то, кто является узким местом.
- «dim задаёт только задержку, кривые склеятся после перемасштабирования
  времени на `escape_epoch`» — нет. При одинаковом `epoch/escape = 3`
  остаточная ошибка 0.4285 / 0.1185 / 0.0685 / 0.0355 для dim 8 / 12 / 16 / 32.
  Кривые расслоены по dim: узкие модели не просто медленнее, они хуже в
  каждый сопоставимый момент.
- «Старая capacity-серия отбирала чекпойнт по training loss» — нет, отбор по
  валидационной точности был и там (`if probe > best_acc[0]`), а loss-отбор
  стоял под `if False:`. Утверждение было построено на docstring, а не на коде.

## 6. Идёт прямо сейчас (запущено 6 августа 23:11)

Три прогона, финиш примерно в 02:15 7 августа:

```bash
cd ~/qubitrino-projects/agi/phef
for S in 0 1 2; do
  LC_ALL=C PYTHONPATH=. nohup python -u experiments/analyze_memory.py \
    --n-segments 256 --n-keys 512 --key-dim 32 --dim 8 \
    --epochs 1000000 --batch-size 256 --eval-batch-size 512 --eval-batches 20 \
    --use-best --acc-every 1000 --acc-n 2048 --seed $S --world gpu \
    --out results/v4/long_dim8_gpu_s${S}_e1M.json \
    > logs/long_dim8_gpu_s${S}_e1M.log 2>&1 &
done
```

**Вопрос прогона:** упирается ли dim 8 в настоящий потолок вместимости или
просто медленно сходится. Экстраполяция по 30000-эпохной истории давала от
276 тысяч до 8 миллионов эпох до `sel_acc` 0.99 — разброс в тридцать раз,
поэтому это лишь порядок величины.

**Как разбирать результат:**

```bash
cd ~/qubitrino-projects/agi/phef
LC_ALL=C python - <<'PY'
import json, glob, re, math
for p in sorted(glob.glob('results/v4/long_dim8_gpu_s*_e1M.json')):
    r = json.load(open(p)); s = re.search(r'_s(\d+)_', p).group(1)
    tail = [x for x in r['history'] if x['epoch'] >= 700000]
    xs = [math.log(x['epoch']) for x in tail]
    ys = [math.log(max(1e-6, 1.0-x['sel_acc'])) for x in tail]
    n=len(xs); mx=sum(xs)/n; my=sum(ys)/n
    k = sum((a-mx)*(b-my) for a,b in zip(xs,ys))/sum((a-mx)**2 for a in xs)
    print(f"s{s}: answer {r['answer_acc']:.4f} soft {r['answer_acc_soft']:.4f} "
          f"mg_top1 {r['oracle_bounds']['mg_top1']:.4f} escape {r['escape_epoch']} "
          f"drop {r['drop_recent_remote']:.4f} наклон@700k+ {k:+.3f}")
PY
```

Критерии интерпретации:
- `mg_top1` → 1.0, наклон около нуля, три сида сошлись в одну точку ⇒
  **потолка нет**, есть только медленная сходимость. Тогда весь раздел про
  capacity переписывается как кривая скорости обучения.
- `mg_top1` застрял ниже 1.0, наклон около нуля ⇒ **потолок реален**,
  512 ключей в 8 измерениях физически не помещаются. Это самостоятельный
  результат, и тогда надо мерить, при каком `n_keys` потолок исчезает.
- наклон всё ещё заметно отрицательный ⇒ миллиона не хватило, отвечать
  нечем, нужен ещё порядок бюджета либо другой подход.

**Отдельно проверить:** на 8500 эпохе все три прогона были ещё на плато
(лосс 4.03–4.13 при chance 4.1589), тогда как в numpy-мире при dim 8 выход
происходил около 6300. Если `escape_epoch` в итоге окажется сильно позже
6000–7000, гейт GPU-мира надо повторить на dim 8: он проверялся только на
dim 32, где всё сходится за 1667.
