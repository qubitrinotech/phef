## 1. Главный сдвиг понимания

Лестница по `n_segments` (2^17 … 2^21) измеряла **не ёмкость памяти**, а обучаемость
на длинных последовательностях. Ёмкость определяется числом различимых ключей при
данном `key_dim`; длина эпизода в предел не входит.

Измерение (один и тот же checkpoint `scr_s524288_seed7_rw0125_e6000.pt`):

| n_keys | S = 2^19 | S = 2^21 |
|---|---|---|
| 512 | 0.9985 | 0.9941 |
| 4096 | 0.9707 | 0.9727 |
| 32768 | 0.8877 | 0.8809 |

Четырёхкратный рост S не изменил ни одного значения.

## 2. Возражение про давность закрыто различающим измерением

Опасение было такое: при 512 ключах последняя запись целевого ключа лежит близко к
концу эпизода, поэтому шанс 1/S завышает трудность задачи.

- Средняя дистанция цели от конца эпизода равна примерно `n_keys`, а **не** `S/n_keys`.
  Замеры: `n_keys=512` → dist_mean 515 при S=2^19 и 499 при S=2^21.
- Профиль точности по абсолютной дистанции **ровный**. При `n_keys=32768` дальний
  бакет доходит до 199 950 событий: 0.8516 против 0.8906 в ближнем (256 эпизодов на
  бакет, в пределах шума). При `n_keys=16384` дальний бакет (до 129 886) даже выше
  ближнего.
- При `n_keys=65536`, S=2^19 наблюдается мягкий спад: 0.8789 в ближнем бакете против
  0.7344 в дальнем (до 479 060). Это единственный случай спада, и он на порядок меньше
  падения от роста числа ключей.

**Вывод.** Адресация содержательная, а не рецентная. Корректная формулировка результата:
модель находит нужную запись на дистанциях до 5×10^5 событий при chance 1/64.

### Инструменты

- `experiments/probe_recency.py` (существовал ранее, **не менялся**) для этой задачи
  непригоден: он режет дистанцию в **долях** эпизода, поэтому все эпизоды падают в
  bucket 0. Плюс он требует `config` внутри `.pt`, чего в наших checkpoint-ах нет —
  для его запуска делался shim `results/probeshim_scr_s524288_seed7_rw0125.pt`.
  Его собственный замер: slot_acc 0.9985, tie_rate 0.0000,
  `recency_scale/score_scale = 0.5621`.
- `experiments/probe_distance_profile.py` (новый, закоммичен в `3f68585`) — квантильные
  бакеты по **абсолютной** дистанции, печатает answer/slot/last и профиль по бакетам.
  **Известный дефект:** поле `expected_dist_uniform` в его JSON считается как
  `S/n_keys` и неверно — игнорировать, правка не внесена.

## 4. retrieval_weight — ручка ёмкости по ключам

Изоляция на S=65536, seed 3, всё остальное идентично:

| n_keys | rw = 1.0 | rw = 0.125 | 0.125 → 1.0 @1000 |
|---|---|---|---|
| 512 | 1.0000 | 1.0000 | — |
| 4096 | 0.9980 | 0.9844 | **0.9990** |
| 32768 | 0.9902 | 0.9434 | **0.9951** |
| 65536 | 0.9873 | 0.9229 | **0.9922** |

Двухфазное расписание обходит оба крайних варианта: escape 750 как у низкого веса,
best 1.0000 @4000 (раньше обоих), ёмкость выше обоих. Обмена «escape против ёмкости»
нет — низкий вес нужен только для выхода с плато, дальше он мешает.

Воспроизведение на seed 4: 0.9980 / 0.9941 / 0.9951 при 4096 / 32768 / 65536,
escape 250, best 1.0000 @4000, контроли PASS.

**Реализация** (`experiments/train_recall.py`, коммит `7627ee8`): флаги
`--retrieval-weight-late` (по умолчанию −1.0 = выключено) и
`--retrieval-weight-switch-epoch` (по умолчанию 0 = выключено); guard падает, если
задан switch без late. Поведение по умолчанию не изменено.

## 5. Расписание не переносится на длинные эпизоды

S=524288, seed 7, переключение 0.125 → 1.0 на эпохе 2000 (escape был на 250):

- до 2000 траектория как у прежнего прогона, sel_acc 0.7266 @2000;
- после переключения обвал: 0.0469 @2250 → 0.0176 @2750 → 0.0176 @4250, без восстановления
  за 2250 эпох;
- retrieval-член: 7.3612 @2000 → 9.07 @2100 → 19.93 @2200 → 49.57 @2400 → 104.81 @2600 →
  137.09 @3000, при неизменном answer ≈ 4.16.

Та же подпись, что при провалах 2^20 из нуля: retrieval 13.86 → 396.56 при rw 0.0625 и
→ 428.52 при rw 0.125. Понижение lr до 1e-4 на 2^20 расхождение снимало
(13.8631 → 13.6926 монотонно), но escape к эпохе 3750 не наступил.

**Объединяющий вывод.** Барьер 2^20 и обвал после переключения — одно явление: при
большом S произведение веса retrieval на lr выводит оптимизацию из устойчивости.
Прогон убит, GPU освобождена.

## 6. Перенос ёмкости между разными S: частичный успех

Идея: ёмкость по ключам — свойство энкодера ключей, а S при оценке на неё не влияет (§1).
Значит поднимать вес на длинных эпизодах не нужно: можно коротко дообучить готовый 2^19
checkpoint на S=65536 с rw=1.0 и мерить ёмкость на любом S.

Прогон: `--init-checkpoint results/scr_s524288_seed7_rw0125_e6000.pt`, S=65536, rw 1.0,
lr 1e-4, 1500 эпох, seed 7. Сошёлся мгновенно: best 1.0000 уже на эпохе 250, escape 250.

Критерий был зафиксирован до старта: ёмкость при 65536 ключах выше 0.95 и сохранность
длинных эпизодов около 0.99.

| замер | до | после |
|---|---|---|
| n_keys 4096, S=2^19 | 0.9707 | 0.9805 |
| n_keys 32768, S=2^19 | 0.8877 | 0.9092 |
| n_keys 65536, S=2^19 | 0.8257 | **0.8662** |
| n_keys 512, S=2^19 | 0.9985 | 0.9961 |
| n_keys 512, S=2^21 | 0.9941 | 0.9980 |

**Критерий не выполнен**: 0.8662 против требуемых 0.95. Но эффект однонаправленный и
длинные эпизоды не пострадали.

**Вывод.** Перенос между разными S безопасен в обе стороны. Ёмкость по ключам
закладывается в основном на ранней фазе обучения и дообучением потом добирается лишь
частично (+0.04), далеко не дотягивая до 0.9922 у модели, обученной на малом S с нуля.

## 8. Открытые задачи, по значимости

1. **Ранняя фаза с высоким весом на малом S, затем перенос на длинный S.** Прямое
   следствие §6: если ёмкость закладывается рано, порядок надо перевернуть — обучать
   с rw=1.0 на S=65536 до конца, затем `--init-checkpoint` и продолжать на S=524288 с
   низким весом. Проверить, сохранится ли ёмкость 0.99 после долгой фазы на большом S.
2. **`key_dim=64` не проверен.** Готовый `scr_s262144_seed7_kd64_e4000.pt` **негоден**:
   `answer_acc 0.1181`, `retrieval_weight 1.0`, не обучился. Нужен новый прогон; дешёвый
   стенд S=65536 занимает около 5–10 минут на 6000 эпох. Ожидание: кривая §3 сдвинется
   вправо примерно на двойку по log2 n_keys.
3. **Устойчивость при большом S.** Гипотеза: нормировать retrieval-CE на log(S) либо
   снижать lr пропорционально S. Различающее измерение не поставлено.
4. **Seeds 8 и 9 на 2^19** (~4 ч каждый), чтобы ступень стояла на трёх seed.
5. **Расхождение slot и answer** при 65536 ключах у `scr_s262144_rw025`: slot 0.9004
   против answer 0.8848 — отдельный механизм ошибки декодирования значения, не
   интерференция ключей. Не исследовано.
6. **Хард vs софт answer-CE** — различающее измерение так и не сделано (предсказание:
   hard ≈ 0.0–0.3, soft ≈ 4.16).
7. Поправить `expected_dist_uniform` в `probe_distance_profile.py` (§2).

## 11. Шаблоны команд

Обучение:

```bash
cd ~/qubitrino-projects/agi/phef; export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True; \
setsid nohup env LC_ALL=C PYTHONPATH=. /home/linux/qubitrino-projects/agi/venv/bin/python -u \
experiments/train_recall.py --n-keys 512 --n-values 64 --n-segments S --overwrite-p 0.3 \
--key-dim 32 --dim 128 --batch-size 32 --epochs N --lr 3e-4 --weight-decay 1e-4 \
--retrieval-weight W --aux-value-weight 0.01 --hard-eval --eval-batch-size 16 \
--eval-batches 64 --use-best --acc-every 250 --acc-n 512 --seed K \
--out results/TAG.json --best-out results/TAG_best.pt > logs/TAG.log 2>&1 < /dev/null & disown
```

Дополнительно: `--init-checkpoint <path>` для старта из готовых весов (ни один параметр
не зависит от `n_segments`, загружается 16 тензоров, skipped=0);
`--retrieval-weight-late W2 --retrieval-weight-switch-epoch E` для двухфазного веса.

Профиль по дистанции и ёмкость по ключам:

```bash
env LC_ALL=C PYTHONPATH=. /home/linux/qubitrino-projects/agi/venv/bin/python -u \
experiments/probe_distance_profile.py --checkpoint results/TAG_best.pt \
--n-segments S --key-dim 32 --n-keys K --seed N --eval-batch-size 8 \
--eval-batches 128 --n-buckets 4 --out results/probe_dist_TAG_keysK.json
```

Независимая оценка по §8:

```bash
env LC_ALL=C PYTHONPATH=. /home/linux/qubitrino-projects/agi/venv/bin/python -u \
experiments/eval_recall_checkpoint.py --checkpoint results/TAG_best.pt \
--n-segments S --eval-batch-size B --eval-batches K --seed N --out results/TAG_eval16384.json
```

B×K держать равным 16384. VRAM ≈ batch × S: 9.7 GB при (16, 2^20) или (8, 2^21) на оценке,
19.2 GB при (32, 2^20) на обучении.

Мониторинг: `tail -f logs/TAG.log | grep --line-buffered "sel_acc"`.
Проверка живости молчащего процесса: `ps -o etimes=,times=,pcpu=,rss= -p PID` дважды с
интервалом 60 с. JSON не существует, пока прогон не завершён.
