## 1. Критический дефект: `--use-best` не работал

В `experiments/analyze_memory.py` блок отбора чекпойнта вызывал
`quick_acc(model, world, device, n=2048)`, но **функция не была
определена**, а переменной `world` не существовало (есть `train_world`
и `eval_world`). Рядом висел мёртвый блок `if False:` — остаток старого
отбора по loss.

Следствие: любой прогон с `--use-best` падал с `NameError` на 250-й эпохе.
Переделка приоритета 1 была начата и не дописана.

### Исправление

* написана `quick_acc(model, world, device, n, batch_size)`;
* добавлен третий мир `sel_world` с `seed + 200_000` — отбор не должен
  идти по `eval_world`, на котором печатается финальный `analyze`;
* мёртвый блок удалён, отбор идёт строго по `probe > best_acc`;
* флаги `--acc-every` (250) и `--acc-n` (2048).

### Проверка исправления

Регрессия на расходящейся конфигурации (kd2, seg 256, 6000 эпох):

| эпоха | 2250 | 6000 |
|---|---:|---:|
| sel_acc | 0.7534 | 0.4688 |

Без отбора итоговый чекпойнт был бы с эпохи 6000. Отбор по accuracy
вернул 0.7534 — разница 0.28 абсолютной точности между «отчёт с мусором»
и «отчёт с числом».

## 2. Две серии в `results/`: загадка kd2

Прошлый отчёт утверждал: «отбор чекпойнта по training loss выбирает
вырожденные recency-решения: kd2 drop 0.847 вместо 0.051». Сравнение
`run_kd_curve.sh` и `run_kd_curve_v2.sh` показало, что скрипты
отличаются **ровно одним флагом**: v2 запускается с `--use-best`,
curve — без него. Всё остальное идентично (256 сегментов, 512 ключей,
3000 эпох, batch 512, сиды 0/1/2).

| key_dim | acc curve | acc v2 | drop curve | drop v2 |
|---:|---:|---:|---:|---:|
| 2 | 0.8239 | 0.5229 | 0.0510 | 0.8467 |
| 3 | 0.9955 | 0.9737 | 0.0124 | 0.0968 |
| 4 | 0.9960 | 0.9955 | 0.0200 | 0.0215 |
| 6 | 0.9988 | 0.9986 | 0.0035 | 0.0059 |

**Уточнение формулировки:** дефектен был отбор *по loss*, а не отбор
как таковой. Baseline для сравнения — финальная эпоха (`curve_*`),
а не «правильный отбор». Числа таблиц 2.2 и 2.5 прошлого отчёта взяты
из `curve_*` и остаются в силе.

Независимое воспроизведение kd3 текущим кодом: `answer_acc = 0.9951`
против отчётных 0.9955, drop 0.019 против 0.012.

## 3. Escape нельзя мерить по loss

Порог `loss < chance - 0.10` давал ложный True; заменён в прошлом отчёте
на `loss < chance/2`. Новый порог оказался ложным в другую сторону.

| прогон | точность | loss | вердикт по loss |
|---|---:|---:|---|
| kd2, seg 256 | 0.8277 | 3.54 | не покинула плато |
| dim 8, seg 256 | 0.4216 | 3.36 | не покинула плато |

Причина: loss измеряет уверенность, accuracy — порядок скоров. На этой
задаче они расходятся (прошлый отчёт фиксировал расхождение до 40 раз).

**Исправление:** `escape_epoch` фиксируется внутри блока `quick_acc`
по условию `probe > escape_factor × chance`, дефолт `escape_factor = 2.0`.
Критерий и порог пишутся в JSON (`escape_criterion`, `escape_threshold`).

Пересчёт всех прогонов серии по единому критерию из логов изменил
картину качественно: для `dim 8` escape оказался 6000–6750, а не
15500–22000, как показывал loss-критерий.

## 4. Предел ёмкости: кривая по ширине представления

Постановка по приоритету 2 прошлого отчёта: фиксируем 256 событий и
`key_dim = 32` (геометрия не мешает), снижаем `dim`. Бюджет 12000 эпох
для `dim ≥ 12`, 30000 для `dim 8`. Три сида на точку.

| dim | n | accuracy | sd | drop recent→remote | escape |
|---:|---:|---:|---:|---:|---:|
| 128 | 3 | 0.9997 | 0.0003 | 0.0019 | 750 |
| 64 | 3 | 0.9995 | 0.0001 | 0.0018 | 1000 |
| 32 | 3 | 0.9983 | 0.0005 | 0.0125 | 1667 |
| 16 | 3 | 0.9837 | 0.0076 | 0.0900 | 3500 |
| 12 | 3 | 0.9644 | 0.0007 | 0.1367 | 3917 |
| 8 | 3 | 0.8415 | 0.0837 | 0.3503 | 6417 |

`oracle m0.05 = 1.0000` во всех 18 прогонах — ключи полностью
разделимы, геометрия исключена как объяснение.

### 4.1 Степенной закон времени обучения

Регрессия по логарифмам: **escape ≈ 750 × (128/dim)^0.79**.

Сжатие ширины в 16 раз отодвигает фазовый переход в 8.6 раза.
Зависимость сублинейная: удвоение сжатия стоит примерно 1.33× эпох.
Правило `epochs ≈ 8 × n_segments` из прошлого отчёта применимо только
при широком представлении.

### 4.2 Характер деградации

Предел не является резким порогом. До `dim 12` точность падает плавно
при малом разбросе (sd ≤ 0.0076). На `dim 8` меняется качество режима:

* sd точности растёт до 0.0837 — в 11 раз против `dim 12`;
* escape при этом остаётся стабильным (6000–6750, sd 382);
* итоговые точности расходятся: 0.766 / 0.827 / 0.932 после 30000 эпох.

То есть выход с плато происходит одинаково быстро, а **скорость подъёма
после него** теряет воспроизводимость.

### 4.3 Механизм компенсации

| dim | 128 | 64 | 32 | 16 | 12 | 8 |
|---|---:|---:|---:|---:|---:|---:|
| score_scale | 3.69 | 5.40 | 7.83 | 8.92 | 8.88 | 17.61 |
| memory_gate | 3.02 | 3.36 | 4.03 | 4.23 | 4.09 | 8.55 |
| enc_m0.05 | 0.994 | 0.734 | 0.213 | 0.120 | 0.020 | 0.000 |

Модель компенсирует узость представления заострением softmax.
До `dim 12` рост плавный и упирается в ~9; на `dim 8` срывается к 17.6
вместе с удвоением `memory_gate` — качественно другой режим.

`enc_m0.05` падает с 0.994 до 0.000 при неизменном входном
`m0.05 = 1.0000`: `key_encoder` не просто «не улучшает» разделимость,
как было записано в опровергнутых гипотезах, а **уничтожает** её тем
сильнее, чем уже представление.

## 5. Эмерджентная адресация: полный набор контролей

`experiments/train_recall.py`, `--retrieval-weight 0`, seg 256,
`key_dim 32`, `dim 128`, 12000 эпох, три сида. В логе `retrieval 0.0000`
на каждой эпохе — сигнал «найди нужное событие» отсутствует полностью.

| seed | best epoch | answer | ×chance | retrieval | ×chance | shuffled | masked | escape | статус |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---|
| 0 | 10250 | 0.9930 | 63.6 | 0.9998 | 256.0 | 0.0221 | 0.0178 | 750 | PASS |
| 1 | 10250 | 0.9949 | 63.7 | 0.9998 | 256.0 | 0.0145 | 0.0145 | 750 | PASS |
| 2 | 12000 | 0.9941 | 63.6 | 1.0000 | 256.0 | 0.0148 | 0.0162 | 750 | PASS |

Разброс `answer` — 0.00195. `retrieval` в среднем 0.99987, то есть
256-кратное превышение chance при нулевом retrieval-loss.

### Контроли

* **baseline без памяти:** 0.015820 при chance 0.015625, статус
  `baseline_at_chance` — задача не протекает;
* **shuffled-memory probe:** максимум 0.0221 против порога 2×chance =
  0.03125 — перемешивание памяти между элементами батча роняет точность
  в 45 раз;
* **masked memory:** максимум 0.0178 — при отключённом канале памяти
  точность на chance, вся информация идёт через память;
* **ключи пересэмплируются каждый батч** — lookup-таблица структурно
  невозможна.

Вердикт печатается машиной (`control_status`), а не собирается вручную
из отдельных прогонов.

## 7. Что осталось нерешённым

### Предел через `dim` найден, через слои — нет

Приоритет 2 прошлого отчёта предлагал резать «число слоёв и голов».
В `phef/model.py` слоёв и голов нет: `PHEF` — это `key_encoder`,
`query_encoder`, softmax-считывание и `head`, без стека трансформерных
блоков. Пункт неприменим как сформулирован; аналог — линеаризация
энкодеров (убрать GELU, заменить двухслойный `key_encoder` линейным).

### Нестабильность на `dim 8` не объяснена

Escape воспроизводим (6000–6750), итоговая точность — нет (0.77–0.93).
Требуется больше сидов и, вероятно, диагностика траектории после
перехода.

### Неприменённые пункты прошлого отчёта

* soft-oracle вместо фиксированного margin 0.05 (энтропия распределения
  похожестей или top-k recall);
* семантика `recency_scale` — наблюдались значения 2.60 и 1.53 при одной
  конфигурации;
* фиксация смены семантики генератора: запрос выбирается по случайному
  сегменту (`pick = rng.integers(0, n_segments)`), а не по уникальному
  слоту; потолок без recency изменился 0.6656 → 0.3857 (seg 256).

### Неиспользуемый код

`phef/memory.py` (`EventMemory` с top-k rerank) не импортируется нигде.
`PHEF` реализует собственное считывание. Кроме того, `EventMemory.read`
принимает `query_key` как индексы для `nn.Embedding`, то есть совместим
только с `symbolic=True` миром.

## 8. Ключевые выводы

**Content-based адресация возникает эмерджентно** без retrieval-сигнала
и подтверждена полным набором контролей на трёх сидах: retrieval 0.9999
при chance 1/256, обвал до chance при перемешивании и отключении памяти,
baseline без памяти ровно на chance.

**Предел ёмкости представления найден и описан.** При 256 событиях и
идеальной геометрии ключей точность держится выше 0.998 до `dim 32`,
снижается до 0.984 при `dim 16` и 0.964 при `dim 12`, падает до
0.84 ± 0.08 при `dim 8`. Ограничение проявляется не как порог, а как
одновременный рост просадки по давности и потеря воспроизводимости.

**Цена сжатия — время обучения по степенному закону**
`escape ≈ 750 × (128/dim)^0.79`, зависимость сублинейная.

**Методологический вывод:** на этой задаче loss непригоден и для отбора
чекпойнта, и для детекции выхода с плато. Оба критерия должны считаться
по валидационной accuracy. Без этого длинные прогоны недостоверны —
что и подтвердилось на kd2, где отбор по последней эпохе дал бы 0.4688
вместо 0.7534.

## 9. Воспроизведение

```bash
cd ~/qubitrino-projects/agi/phef

# кривая ёмкости
for D in 128 64 32 16 12; do for S in 0 1 2; do
  PYTHONPATH=. python -u experiments/analyze_memory.py \
    --n-segments 256 --n-keys 512 --key-dim 32 --dim $D \
    --epochs 12000 --batch-size 256 --eval-batch-size 512 --eval-batches 20 \
    --use-best --acc-every 250 --acc-n 2048 --seed $S \
    --out results/capacity/dim${D}_kd32_seg256_s${S}_e12k.json
done; done

# dim 8 требует 30000 эпох
for S in 0 1 2; do
  PYTHONPATH=. python -u experiments/analyze_memory.py \
    --n-segments 256 --n-keys 512 --key-dim 32 --dim 8 \
    --epochs 30000 --batch-size 256 --eval-batch-size 512 --eval-batches 20 \
    --use-best --acc-every 250 --acc-n 2048 --seed $S \
    --out results/capacity/dim8_kd32_seg256_s${S}_e30k.json
done

# эмерджентная адресация
for S in 0 1 2; do
  PYTHONPATH=. python -u experiments/train_recall.py \
    --n-segments 256 --n-keys 512 --key-dim 32 --dim 128 \
    --epochs 12000 --batch-size 256 --eval-batch-size 512 \
    --retrieval-weight 0 --use-best --acc-every 250 --acc-n 2048 --seed $S \
    --out results/recall/recall_seg256_rw0_s${S}.json
done

# baseline без памяти
PYTHONPATH=. python -u experiments/train_recall.py \
  --n-segments 256 --n-keys 512 --key-dim 32 --dim 128 \
  --epochs 3000 --batch-size 256 --no-memory --seed 0 \
  --out results/recall/recall_seg256_nomem_s0.json

# сводка
PYTHONPATH=. python -u experiments/collect_results.py \
  --root results/capacity --pattern "*.json" --exclude _superseded \
  --out output/capacity_final.csv
```

Железо: RTX 4090. Прогон 12000 эпох при `dim 128` — около 10 минут,
30000 эпох при `dim 8` — около 24 минут. Узкое место не в вычислениях
(~2 TFLOP на прогон), а в числе шагов: 20.8 эпох/сек при генерации мира
на CPU.

**Важно:** запуск только с `PYTHONPATH=.` из корня проекта.
Разбор логов — только с `LC_ALL=C`, иначе `awk` и `sort -g` в русской
локали интерпретируют точку как разделитель тысяч и молча возвращают
неверный результат.
