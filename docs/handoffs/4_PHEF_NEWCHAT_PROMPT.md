## 2. Задача, которую решает модель

Мир `phef/world.py`, класс `BranchingWorld` — прочитан, вот что в нём есть:

- эпизод состоит из `n_segments` событий; каждое событие пишет значение в
  слот, слоты сэмплируются равномерно из `n_keys`;
- `overwrite_p=0.3` дополнительно заставляет часть событий переписывать
  ранее использованный слот;
- запрос — случайный слот из встреченных, правильный ответ — значение
  **последней** записи в этот слот
  (`answer_positions = n_segments - 1 - argmax(match[:, ::-1], axis=1)`);
- кодбук ключей `standard_normal((bs, n_keys, key_dim))` с нормировкой
  **пересэмплируется каждый батч**, поэтому выучить таблицу ключей
  невозможно в принципе.

Следствия, которые надо держать в голове:
- `n_keys` управляет **частотой перезаписи**, а не размером запоминаемого
  набора. При `n_keys` 64 на 256 сегментов каждый слот повторяется в среднем
  четырежды и задача становится задачей на давность;
- число одновременно удерживаемых событий равно `n_segments`, всегда;
  различных слотов в эпизоде не больше `min(n_keys, n_segments)`;
- **параметр вместимости — это `n_segments`, и его до сих пор не варьировали.**

`results/v4/long_dim8_gpu_s{0,1,2}_e1M.json`, GPU-мир, `--acc-every 1000`.

1. **Плато достигнуто.** Наклоны `log(1−sel_acc)` по `log(epoch)` на последней
   трети неотрицательны, у сида 0 лучший чекпойнт на 591000 эпохе из миллиона.
   Дальнейшее обучение при dim 8 не даёт ничего.

   геометрии, а не недообучение.

## 5. Что отозвано (не воспроизводить эти утверждения)

- ~~«Разрыв hard/soft — свойство размерности, superposition растёт при
  сужении dim»~~ — при dim 8 разрыв схлопнулся с +0.1308 (30k эпох) до
  +0.0044 (1M эпох). Значит разрыв — **эффект недообучения**, а точки
  dim 12–128 в таблице выше сняты на 12000 эпохах, то есть в той же
  несошедшейся зоне. Требует перепроверки на длинном бюджете.
- ~~«512 ключей в 8 измерениях физически не помещаются»~~ — неверная
  формулировка. Одновременно удерживается `n_segments` = 256 событий,
  а не `n_keys`. Правильная формулировка потолка: 256 событий в 8 измерениях.
- ~~«Меньший `n_keys` — более лёгкая задача»~~ — наоборот, см. раздел 2.
- ~~«Отставание факта от `mg_top1` постоянно по всей кривой»~~ — абсолютное
  отставание падает с ростом dim и обнуляется при сходимости.
- ~~«dim задаёт только задержку, кривые склеятся после перемасштабирования
  времени на escape»~~ — нет. При `epoch/escape = 3` остаточная ошибка
  0.4285 / 0.1185 / 0.0685 / 0.0355 для dim 8 / 12 / 16 / 32.
- ~~«Старая capacity-серия отбирала чекпойнт по training loss»~~ — нет,
  отбор шёл по валидационной точности и там; loss-блок стоял под `if False:`.
- ~~«key_encoder уничтожает разделимость»~~ — артефакт метрики. Косинусные
  `enc_*` считались после `F.normalize`, а модель скорит `dot/sqrt(dim)` без
  нормировки. В геометрии модели `mg_top1` = 0.9988 при dim 32.
  Раздел 4.3 отчёта требует переписывания.
- **`tie_rate` бесполезен по построению** — при непрерывных ключах ничьих
  не бывает (0.0000–0.0001).
- **Термин «вместимость» в применении к таблице раздела 3** снимается:
  ни одна точка на своём бюджете не сошлась, таблица меряет положение
  траектории на фиксированной эпохе.

## 6. Что считается прямо сейчас

Запущено 02:12, финиш около 04:27. Четыре процесса, GPU-мир, 74 эпохи/сек
каждый, GPU 99%, 2.4 ГБ, PID 699089–699092.

```bash
for NK in 64 128 256 384; do
  LC_ALL=C PYTHONPATH=. nohup python -u experiments/analyze_memory.py \
    --n-segments 256 --n-keys $NK --key-dim 32 --dim 8 \
    --epochs 600000 --batch-size 256 --eval-batch-size 512 --eval-batches 20 \
    --use-best --acc-every 500 --acc-n 2048 --seed 0 --world gpu \
    --out results/v4/nk${NK}_dim8_gpu_s0_e600k.json \
    > logs/nk${NK}_dim8_gpu_s0_e600k.log 2>&1 &
done
```

Серия была задумана как развёртка вместимости — **это была ошибка
постановки**, `n_keys` меряет не вместимость (см. раздел 2). Но серия всё
равно ценна: она разделяет два источника ошибки. `mg_top1` засчитывает
попадание в **любое** событие с нужным слотом, `answer_acc` требует значение
**последней** записи. Значит при малых `n_keys` расхождение
`mg_top1 − answer_acc` — это чистая цена ошибки давности, а при `n_keys` 512
совпадений слотов почти нет и обе метрики сходятся.

Разбор результата:

```bash
cd ~/qubitrino-projects/agi/phef
LC_ALL=C python - <<'PY'
import json, glob, math
rows=[]
for p in glob.glob('results/v4/nk*_dim8_gpu_s0_e600k.json') + ['results/v4/long_dim8_gpu_s0_e1M.json']:
    r=json.load(open(p)); nk=r['config']['n_keys']
    last=r['history'][-1]['epoch']
    tail=[x for x in r['history'] if x['epoch'] >= 0.7*last]
    xs=[math.log(x['epoch']) for x in tail]
    ys=[math.log(max(1e-6,1.0-x['sel_acc'])) for x in tail]
    n=len(xs); mx=sum(xs)/n; my=sum(ys)/n
    k=sum((a-mx)*(b-my) for a,b in zip(xs,ys))/sum((a-mx)**2 for a in xs)
    rows.append((nk,r['answer_acc'],r['answer_acc_soft'],r['oracle_bounds']['mg_top1'],
                 r['escape_epoch'],r['drop_recent_remote'],r['best_epoch'],k))
print(f"{'nk':>5} {'answer':>7} {'soft':>7} {'gap':>7} {'mg_top1':>8} {'recency':>8} {'escape':>7} {'drop':>6} {'best@':>8} {'наклон':>7}")
for nk,a,s,mg,e,d,be,k in sorted(rows):
    print(f"{nk:5d} {a:7.4f} {s:7.4f} {a-s:+7.4f} {mg:8.4f} {mg-a:8.4f} {e:7d} {d:6.3f} {be:8d} {k:+7.3f}")
PY
```

Критерий сходимости точки: наклон около нуля и `best_epoch` заметно раньше
конца бюджета. Если наклон заметно отрицательный — точка недосчитана,
выводы по ней делать нельзя.
