## 2. Узкое место найдено: `BranchingWorldGPU.batch()`

[ФАКТ] Прочитан фактический код `phef/phef/world_gpu.py`. Сигнатура:
```python
BranchingWorldGPU(n_keys=512, n_values=64, n_segments=256, overwrite_p=0.3,
                  key_dim=32, seed=0, symbolic=False, device='cuda')
```

[ФАКТ] В `batch(self, bs)` при `s = self.n_segments` создаются:
- `values = self._randint(self.n_values, (bs, s))`
- `timestamps = torch.arange(s, device=dev).expand(bs, s).contiguous()`
- `match = slots == query_slots.unsqueeze(1)`
- `rev = torch.flip(match, dims=[1]).float()`, затем `rev.argmax(dim=1)`
- `codebook = torch.randn((bs, self.n_keys, self.key_dim), ...)`, нормализуется
- `event_keys = torch.gather(codebook, 1, slots.unsqueeze(-1).expand(bs, s, self.key_dim))`

[ВЫВОД] `event_keys` имеет форму `bs × n_segments × key_dim`. При `bs=64`, `n_segments=131072`, `key_dim=32` это 268435456 элементов ≈ **1024 MiB во float32** на один вызов.

[ФАКТ] Из кода `analyze_memory.py` (строки 538–566): при `accum_steps=4` первый микробатч берётся до цикла, микробатчи `micro > 0` вызывают `move(train_world.batch(args.batch_size), device)` заново. То есть **4 вызова `batch()` за эпоху**.

[ВЫВОД] Это memory-bound профиль: 4 × 1024 MiB генерации данных на эпоху объясняют и 17.6 с/эпоху, и 40% утилизации GPU при 123 W из 450 W.

[ВЫВОД] `batch_size=128, accum_steps=2` даст 2 вызова по ~2048 MiB — тот же объём через шину памяти. Выигрыш только на накладных расходах запуска ядер, не на пропускной способности. Реальное ускорение требует правки `batch()`: не материализовать `event_keys` через `gather`, а передавать `slots` и `codebook` в модель. Это изменение кода модели — отдельная задача, `phef/model.py` для этого не читался.

[НЕИЗВЕСТНО] Фактическое время одного вызова `batch(64)` на 131072. Микротест был запущен, но упал с `torch.AcceleratorError: CUDA error: out of memory` на `torch.cuda.synchronize()`, потому что GPU в тот момент была занята процессом 1765050 на 24018 MiB. Повторить на свободной карте.
