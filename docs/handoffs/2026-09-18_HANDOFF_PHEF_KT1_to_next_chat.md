## 1. Что такое PHEF и что измеряется

Механизм ассоциативной памяти «latest value under overwrite» с streamed hard retrieval:
поблочное сканирование истории с сохранением лучшего кандидата, **без материализации
плотного тензора оценок формы `(batch_size, n_segments)`**.

### Протокол оценки (`compact_eval_v2_streamed_hard`)

```
n_keys:                 1 073 741 824 = 2^30   (key-ID universe, НЕ число записей)
n_values:               64                     (nominal chance = 1/64 = 0.015625)
overwrite_p:            0.3
key_dim:                32
dim:                    128
eval_batch_size:        2
stream_hard_chunk_size: 65536
conditions:             real -> shuffled -> masked (фиксированный порядок)
```

### Терминология

| Термин | Значение |
|---|---|
| `n_segments` | число событий в траектории памяти |
| `n_eff_mean` | измеренное среднее число активных записей — **основная capacity-величина** |
| `n_keys` | размер пространства ID ключей; определяет статистику коллизий |
| `real` | штатное соответствие памяти и запроса |
| `shuffled` | циклический сдвиг эпизодов памяти между строками батча; пары запрос/ответ сохранены |
| `masked` | вход памяти отключён |

### Существенная деталь реализации

`codebook` нормирован на единичную сферу:
`codebook /= np.linalg.norm(codebook, axis=-1, keepdims=True)`.
Следовательно `||key|| = 1`, per-component std = `1/sqrt(32) ≈ 0.1768`.
`key_scale_from_codebook` измеряет std от фактического тензора, поэтому
**σ численно равна относительному возмущению нормы ключа**: σ=0.3 → шум 30% нормы.
Это следствие именно этой нормировки и должно быть переведено заново, если её уберут.

**Exact hash map обваливается с 256/256 до 0/256 при любом σ > 0.** Это установило
существование ниши неточного ключа.

**Немонотонность baseline сохраняется**: σ=0.42 даёт 5/256, σ=0.50 даёт 8/256 — baseline
«вырос» при большем шуме. Интервалы [0.0084, 0.0449] и [0.0159, 0.0604] перекрываются,
различие не значимо. Закрыто **консервативной монотонной огибающей**: порог при σ
берётся как максимум верхних границ по всем σ' ≥ σ. Порог при 0.42 поднят 0.0449 → 0.0604.
**Вердикт проверен на v2-raw, v3-raw и v3-envelope — не меняется.**

### Диагностические наблюдения

1. `answer_acc ≡ retrieval_acc` в 15 из 24 ячеек; нарушается только при σ ≥ 0.70,
   где retrieval около нуля. Ошибки локализованы в селекции события.
2. `shuffled retrieval = 0/256` на **всех** уровнях σ, все 24 ячейки. Возмущение запроса
   не создаёт ложных срабатываний: деградация есть смещение к соседям по ключевому
   пространству, а не переход к угадыванию.
3. `shuffled answer` вышел за chance-интервал в 6 из 24 ячеек. Множественное сравнение
   без поправки — не находка, но подлежит фиксации. **Существенно:** прежняя формулировка
   отчёта «shuffled answer около chance regime» требует уточнения.
4. Подавление шума энкодером **слабеет** с ростом σ: (1-q_cos)/(1-raw_cos) =
   0.50 → 0.51 → 0.53 → 0.57 → 0.62. Не константа.
5. Узкое место по времени — однопоточная numpy-генерация мира (`_sample_slots`),
   не GPU-скоринг. ~10 s на батч. Wall time НЕ характеризует стоимость streamed retrieval.
6. `masked` при σ>0 гоняется впустую (памяти нет, шум не применяется): ~1.8 часа GPU
   потеряно. Для будущих прогонов нужен флаг `--skip-masked`.

### Зависимость устойчивости от глубины — отдельный результат

При `n_segments = 4096` (`n_eff ≈ 2870`) σ=0.30 давала retrieval **1.0**.
При `n_segments = 14M` (`n_eff ≈ 9.76M`) та же σ=0.30 даёт **0.7773**.

Одна модель, одно возмущение, разная глубина. **Рабочее окно σ сужается с ростом
глубины памяти.** Интервал [0.30, 0.50] есть свойство пары (механизм, глубина), а не
механизма. Следствие для прикладных сценариев: при длинной истории окно будет уже
измеренного — это аргумент против наивного масштабирования истории.

### Итоговая формулировка (использовать дословно)

> При глубине 14M и `n_eff ≈ 9.76M` механизм превосходит квантованный словарь с честно
> подобранным шагом при относительном возмущении query key от 30% до 50% нормы ключа,
> с плавной монотонной деградацией от 0.777 до 0.297. При возмущении 70% словарь
> превосходит механизм; при 100% и выше механизм на уровне случайного угадывания.
> При точном ключе оба доминируются exact hash map. Ширина рабочего окна зависит от
> глубины памяти: при 4096 сегментах возмущение 30% не вызывало деградации.

`from kt1_thresholds import thresholds; THRESH = thresholds(envelope=True)`.
Вердикт от этого не меняется (проверено: все 8 решений идентичны), но печатаемые
числа неверны.

### Пять независимых категорий

| Категория | Оценка для PHEF |
|---|---|
| Subject-matter eligibility | **Улучшилась.** MPEP-обновление 05.12.2025 по прецедентному `Ex parte Desjardins`: оценивать притязание как целое с учётом технологического улучшения в спецификации. USPTO относит «reduced storage, reduced system complexity» к технологическим улучшениям |
| Novelty | Область насыщена: Product Key Memory, Memory Layers at Scale, UltraMem, Titans/MIRAS |
| **Inventive step** | **Слабейшая позиция.** MIRAS формализует архитектуру памяти через memory structure / attentional bias / retention gate / memory algorithm; постановка PHEF внутри опубликованного фреймворка |
| Enablement | риск преждевременной provisional |
| **Freedom-to-operate** | независима от остальных; **собственный патент не даёт FTO** |

### Прямое заключение

«Нейросетевая ассоциативная память» и «streamed retrieval» как таковые с высокой
вероятностью непатентоспособны. Поблочная обработка для избежания материализации
больших промежуточных тензоров — устоявшийся приём (flash-attention-класс); MIRAS
применяет чанкованные batched matmul для того же.

**Потенциальная узкая опора:** способ inference-time retrieval над памятью длины N при
бюджете VRAM, инвариантном к N в части тензора оценок, включая tie-семантику через
границы чанков, **при документированном профиле потребления ресурсов**.
Определяющее слово — документированном. Измерения есть: 15M ≈18.12 GiB, 16M ≈19.32 GiB,
17M ≈20.52 GiB, wall time 464.7→566.6 s, граница аллокатора зафиксирована.

**Блокирующее условие: до KT-3 нет counterfactual против attention** — нечего описывать
как improvement относительно доминирующей альтернативы.

### Российский трек

296-ФЗ от 04.08.2026 вступает в силу **01.01.2027**: ст. 1350 ГК прямо допускает
патентование технических решений, реализуемых программным способом. **Существеннее:**
ст. 1351 распространяет на такие решения режим полезной модели, где изобретательский
уровень при экспертизе не проверяется и не может быть основанием оспаривания.
Учитывая слабость позиции по inventive step — это направление обязано попасть в вопросы
к поверенному РФ.

### Патент Google по progressive learning

US 11 450 096 B2 / US 12 062 227 B2: обучение с разной величиной регуляризации на разных
итерациях. **Запрета на деятельность не образует** — объём определяется формулой, не
заголовком; streamed inference retrieval в иной плоскости. **Но образует риск для
curriculum-направления (KT-6)** и требует профессионального FTO до коммерциализации.

### Что нельзя публиковать до приоритетной подачи

Детали поблочного сканирования (размер чанка 65536, механизм поддержания лучшего
кандидата, tie-семантика через границы чанков); специфику staged/curriculum transfer;
точную связь архитектурных решений с профилем ресурсов.

Безопасно: факт оценки на 14M–17M, агрегированные accuracy и conditions, протокол на
уровне детализации существующего отчёта.

**Следствие:** demo-вариант «Trace Viewer» (пошаговая визуализация сканирования по
чанкам) публично НЕ разворачивать до IP-решения — он визуализирует ровно закрытые
элементы.

## 6. Прикладные сценарии: фильтр применимости

Механизм имеет шанс превзойти hash-map только при одновременном выполнении:
**C1** ключ неточен/непрерывен/семантичен/дрейфует; **C2** retrieval должен быть
дифференцируем внутри end-to-end обучаемой модели; **C3** семантика «latest value under
overwrite» содержательно корректна; **C4** есть ограничение памяти/compute или нужна
online-адаптация.

Приоритетные: A-1 телеметрия (прогноз следующего состояния), A-2 память робота о
состоянии среды, A-3 adaptive cache admission, A-4 поиск по логограммам (client-side).

Отклонены: замена RAG для документов (**C3 инвертировано**: документ не аннулируется
новым), классификация root cause (3 из 4 условий не выполнены), верификация
распределённого реестра (неизменяемость vs перезапись — C3 инвертировано), финансовый
трейдинг (backtest overfitting + репутационный риск).

**Корректная формулировка ценности:** дифференцируемый слой, реализующий вытеснение
устаревших значений по приближённому ключу внутри end-to-end обучаемой модели, при
бюджете памяти, инвариантном к длине истории в части тензора оценок.
**Некорректная:** память общего назначения.


Последняя строка критична: **установлен ли FAISS**. Без него KT-2 требует установки,
и это отдельный шаг (FAISS под python 3.14 может не собраться — не предполагать, проверить).

### Шаг 1. Закрыть незакрытый дефект

Исправить хардкод `THRESH` в `kt1_progress.py` на импорт из `kt1_thresholds`.

### Шаг 2. РЕШЕНИЕ ПО ПОСТАНОВКЕ KT-2 — обсудить с пользователем

Два взаимоисключающих варианта. Вопрос открыт, пользователь не выбрал.

**Вариант А — сравнение по точности (как в исходном ТЗ).**
FAISS HNSW и IVF-PQ по ~10M векторам `key_dim=32` с recency tie-break, на той же сетке σ.
Измерить accuracy, потребление памяти, латентность запроса, время построения индекса.

*Аргумент против:* HNSW создан для приближённого поиска. Он почти наверняка покроет весь
интервал σ ∈ [0.30, 0.50], где PHEF жив, и покроет лучше — при меньшей памяти и
латентности. Результат предсказуемо отрицательный и малоинформативный.

**Вариант Б — проверка того, что HNSW не умеет в принципе (рекомендуется).**
Измерять не точность, а наличие свойства:
- *дифференцируемость*: обучить end-to-end модель, где retrieval-слой есть индекс, —
  невозможно, индекс не дифференцируем. Измеримо: две конфигурации на одной задаче,
  сравнение достижимого качества;
- *встроенное вытеснение*: для latest-value семантики HNSW нужна внешняя логика — либо
  удаление из индекса (дорого), либо timestamp с постфильтрацией (меняет recall).
  PHEF делает это в скоринге. Измеримо: стоимость обновления при потоке перезаписей.

*Аргумент за:* результат содержателен при любом исходе и ложится прямо в формулировку
ценности из §6. Вариант А при отрицательном исходе не даёт ничего, кроме констатации.

**Честная оценка:** даже при варианте Б возможен исход, закрывающий направление —
если окажется, что постфильтрация по timestamp дёшева и не портит recall, то
преимущество «встроенного вытеснения» исчезает. Это нормально: KT-2 для этого и нужен.

### Шаг 3. После выбора — ТЗ на KT-2 по образцу KT-1

Обязательные элементы: критерии успеха и провала **до** запуска; интервалы Уилсона;
одинаковое число эпизодов у механизма и baseline (урок v1→v3); фиксация артефактов и
коммит с датой.

### Альтернатива: приоритет KT-3 вместо KT-2

Аргумент: KT-3 (parameter-matched attention) — **блокирующее условие патентного трека**
(§5), тогда да KT-2 определяет только позиционирование против ANN. Если горизонт
коммерциализации близок, KT-3 приоритетнее. Решает пользователь.

### Чего НЕ делать

- Не разворачивать публичное demo: до counterfactual против attention оно не имеет
  доказательной силы и создаёт enabling disclosure.
- Не подавать provisional: без KT-3 нет counterfactual, недораскрытая заявка
  необратимо запускает 12-месячный отсчёт.
- Не расширять сетку σ: точка отказа найдена (σ ≥ 1.0 — chance), спад плавный,
  адаптивное уточнение не требуется.
- Не переформулировать вердикт KT-1: он проверен на трёх версиях порогов.
