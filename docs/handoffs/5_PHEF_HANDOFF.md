## 3. Код: что установлено чтением

### 3.1 `phef/world.py` (BranchingWorld, numpy) — 131 строка

- `:33-37` слоты сегментов равномерны по `n_keys`.
- `:39-40` с вероятностью `overwrite_p` сегмент переиспользует слот более раннего;
  нулевой сегмент никогда (`reuse[:, 0] = False`).
- `:42, :46-47` источник переиспользования равномерен по `[0, ts)`.
- `:49-54` подстановка слота-кандидата.
- `:62-66` значения равномерны по `n_values`.
- `:68-71` timestamps — просто `arange(n_segments)`, одинаково для всех эпизодов.
- `:73-74` запрос выбирает **индекс сегмента** равномерно; его слот — слот запроса.
- `:76-81` позиция ответа — **последнее** вхождение слота запроса
  (`argmax` по перевёрнутой маске).
- `:82` ответ — значение в этой позиции.
- `:101-106` кодовая книга пересэмплируется **каждый батч** и нормируется.
  Таблица подстановок структурно невозможна.
- `:111-112` `event_keys = take_along_axis(codebook, slots)` — **все события одного
  слота получают побитово одинаковые ключи**.
- `:116` `query_keys = codebook[rows, query_slots]` — ключ запроса **точно равен**
  ключу событий своего слота. Отсюда наблюдаемое `oracle raw_top1 = 1.000000`.
- `:118-119` `last_slots`, `last_query_slots` — то, чем пользуются метрики по слотам.

### 3.2 `phef/world_gpu.py` (BranchingWorldGPU) — 140 строк

- `:46-47` собственный `torch.Generator(device=...)`, засеянный `seed`.
- `:56, :59-64, :118-121` все розыгрыши идут через него.
- Следствие: **глобальный RNG в цикле обучения не расходуется**, экземпляры миров
  независимы. Побитовой совместимости с numpy-миром нет; сравнивать сиды
  по номеру между мирами нельзя.
- `:125-129` та же логика ключей, что в `world.py:111-116`.

### 3.3 `phef/model.py` (PHEF) — 123 строки

- `:20` `n_segments` сохраняется, но **ни одного параметра не порождает**.
  Число обучаемых весов зависит только от `key_dim`, `dim`, `n_values`.
- `:37-39` три обучаемых скаляра: `recency_scale` (инициализация 0.0),
  `score_scale` (1.0), `memory_gate` (0.0).
- `:51, :69-70, :76` `shuffle` по умолчанию `False`, нигде в
  `analyze_memory.py` не передаётся → `torch.randperm` не исполняется.
  Дропаута в модели нет. Случайности при обучении и оценке нет вовсе.
- `:78` `memory_keys = key_encoder(event_keys)`.
- `:80-84` `semantic = einsum("bd,bsd->bs", query_state, memory_keys) / sqrt(dim)`.
- `:86-89` `recency = timestamps / max(1, n_segments - 1)`, то есть линейный
  наклон от 0 до 1 по позиции.
- `:91-92` `scores = score_scale * semantic + recency_scale * recency`.
- `:96-106` жёсткий ридаут: `tie_count` считается с допуском `1e-6`,
  выбор через `scores.argmax(dim=1)`.
- `:107-113` мягкий ридаут: `softmax(scores)`, взвешенная сумма значений.
- `:115-117` `hidden = norm(query_state + sigmoid(memory_gate) * memory_state)`,
  затем `head`.
- `:119-120` при `return_retrieval=True` возвращается пара `(logits, scores)`.

**Структурное следствие, подтверждённое многократно:** при `recency_scale > 0`
среди событий одного слота (с одинаковыми ключами) аргмакс всегда берёт последнее.
Поэтому `retrieval_acc ≡ score_top1` тождественно. Проверено: в 60 парах из абляции
максимальное расхождение `|slot − last|` равно 0.000000.

### 3.5 `experiments/probe_recency.py` — 314 строк, создан 8 августа

Абляция слагаемого давности на сохранённых весах, **без обучения**. Загружает `.pt`,
пересобирает `PHEF` из `config`, строит `eval_world = make_world(cfg["seed"] + 100_000)`
заново для каждого множителя (чтобы батчи были одни и те же), домножает

Аргументы: `--glob` (обязателен), `--multipliers` (по умолчанию `1.0 0.5 0.25 0.0 2.0`),
`--eval-batch-size` и `--eval-batches` (по умолчанию `None` → берутся из конфига
чекпойнта), `--n-buckets 8`, `--out`.

Печатает строку «воспроизведение»: сравнивает `answer_acc` при множителе 1.0
с `answer_acc` из одноимённого `.json`. **Эта строка обязана говорить «совпало».**
На всех 15 чекпойнтах совпала побитово.

Оговорка: строка с множителем 0 может слегка плавать между запусками — при точном
равенстве скоров поведение `argmax` на CUDA документацией не гарантировано.
Строки с ненулевой давностью от этого не страдают.

## 4. Установленные результаты

### 4.1 Ошибки давности как отдельного механизма не существует

`answer_acc − retrieval_acc` во всех 15 прогонах развёртки совпадает с моделью
«аргмакс промахнулся мимо слота, но значение случайно совпало», предсказание
`(1 − retrieval_acc) / n_values`: корреляция Пирсона 0.970, среднее отношение
наблюдаемого к предсказанному 1.10, максимальное абсолютное отклонение 0.0008.
Разброс отношения приходится на строки, где сама величина порядка 0.0003 —
это округление печати, не сигнал.

Профиль `slot_acc_by_distance` идёт вплотную к `acc_by_distance` при всех пяти
длинах; расхождение нигде не выходит за 0.011.

### 4.2 Спад по дистанции целиком создаётся слагаемым давности

Абляция на сохранённых весах (`recency_ablation.json`, 15 чекпойнтов × 5 множителей):

| | slot_drop при множителе 1.0 | при 0.0 |
|---|---|---|
| среднее | 0.1895 | −0.0034 |
| размах | 0.0446 … 0.4435 | −0.0429 … +0.0165 |

Знак остатка положителен в 8 случаях из 15 при ожидаемых 7.5 — остаток неотличим
от нуля. Дозовая зависимость строго монотонна по 0 → 0.25 → 0.5 → 1 → 2
во **всех 15** прогонах.

Наклон при этом ничего не добавляет в среднем, он только перераспределяет.
Пример, seg 1024 seed 0: при множителе 1.0 профиль 0.7944 → 0.3509 при агрегате
0.6971; при 0.0 профиль 0.7009 → 0.7281 при агрегате 0.6981.

### 4.3 Но обнулить наклон нельзя

При нулевой давности события одного слота дают равные скоры, аргмакс среди них
произволен, выбирается не последняя запись, и `answer_acc` рушится
(0.7014 → 0.1046 при seg 1024; 0.9798 → 0.4924 при seg 64). Столбец `last`
падает вместе с `answer`, `tie_rate` подскакивает. Наклон реализует правило
«побеждает последняя запись» и он же создаёт спад по дистанции — в текущей
архитектуре это одно и то же слагаемое.

Побочно получена статистика мира (при множителе 0, среднее по 3 сидам):

| seg | 64 | 128 | 256 | 512 | 1024 |
|---|---|---|---|---|---|
| tie_rate | 0.499 | 0.540 | 0.586 | 0.673 | 0.820 |
| событий на слот (= 1/last) | 2.04 | 2.25 | 2.97 | 4.84 | 9.82 |

### 4.4 Обученный recency_scale больше оптимального по точности

Уменьшение `recency_scale` вдвое без дообучения улучшает `answer_acc`
в **15 прогонах из 15**: средний прирост +0.0044, размах +0.0011 … +0.0079,
односторонний знаковый тест p = 3.05e-05. При множителе 0.25 улучшений 14 из 15,
средний прирост +0.0050.

Множитель 0.5 был в списке до того, как результаты стали известны, — подгонки
множителя под данные нет. **Оговорка:** оценка идёт на том же наборе 10240 эпизодов,
на котором посчитан `answer_acc` в JSON; стандартная ошибка одиночного значения
там около 0.004, то есть того же порядка, что эффект. Спасает парность и
согласованность знака, но на независимом наборе это **не перепроверено**
(см. раздел 8.1).

### 4.5 Развёртка по n_segments (dim 8, n_keys 512, key_dim 32, gpu, 200k эпох, 3 сида)

| seg | медиана answer | среднее | размах | escape среднее | отн. разброс escape |
|---|---|---|---|---|---|
| 64 | 0.9798 | 0.9800 | 0.003 | 1917 | 7.5% |
| 128 | 0.9688 | 0.9715 | 0.009 | 3750 | 6.7% |
| 256 | 0.8377 | 0.8776 | 0.140 | 6417 | 8.1% |
| 512 | 0.7814 | 0.7769 | 0.020 | 12417 | 5.1% |
| 1024 | 0.7033 | 0.7794 | 0.232 | 18917 | 5.0% |

Медиана монотонно падает, среднее — нет: при seg 256 и seg 1024 один сид из трёх
попал в заметно лучший бассейн (0.9675 и 0.9336), при seg 512 — ни один.
Бассейн достижим при любой длине, это лотерея инициализации, а не исчерпание
ёмкости. При трёх сидах на точку она мажет кривую сильнее самого эффекта длины.

Степенная подгонка `escape = 63.1 · S^0.833`, R² в логарифмах 0.995, но ошибки
подгонки ±8% и локальные показатели по соседним точкам гуляют 0.61 … 0.97, то есть
не лучше собственного разброса сидов. Как степенной закон держится; точное значение
показателя по пяти точкам заявлять нельзя.

**Бюджет ограничивает все числа.** `best_epoch` в среднем 172633 = 86.3% бюджета;
14 прогонов из 15 нашли лучшую точку в последней четверти. Ни один не вышел на плато.
Все значения точности — оценки снизу, и неизвестно, одинаково ли они занижены
при разных длинах.

### 4.6 Гейт «numpy против gpu» при dim 8 закрыт

Тройка gpu на 30k против тройки numpy на 30k (одинаковый `acc_every` 250):
answer_acc numpy 0.7752 / 0.8296 / 0.9298 против gpu 0.7769 / 0.7835 / 0.8381,
перестановочный тест p = 0.70; escape p = 0.90. Диапазоны вложены по всем шести
сравнивавшимся величинам.

Формулировать честно: это **не подтверждение равенства**, а отсутствие грубого
расхождения при мощности около нуля (минимально достижимое p при 3 на 3 равно 0.10).

Пять из шести прогонов лежат в 0.775 … 0.838, единственный выброс — numpy seed 1
(0.9298), у него же аномальный `drop` 0.194 и максимальный `score_scale` 21.39.
«Два кластера» из старого раздела 4.3 держатся на одном прогоне, попавшем
в хороший бассейн.

### 4.7 Бюджет 30k → 1M при одном мире и сиде

Пары отличаются только `epochs`, `out` и `acc_every` (250 против 1000);
`lr_decay=False`, `use_best=True`, `select_metric=soft`, `lr=1e-3` везде.

| seed | answer | drop | score_scale |
|---|---|---|---|
| 0 | 0.7769 → 0.8111 | 0.473 → 0.198 | 18.54 → 72.67 |
| 1 | 0.7835 → 0.8139 | 0.453 → 0.174 | 18.11 → 74.20 |
| 2 | 0.8381 → 0.9600 | 0.380 → 0.106 | 19.49 → 115.67 |

Три из трёх в одну сторону; односторонний знаковый тест p = 0.125. Падение спада
почти одинаково: −0.275 / −0.279 / −0.274 при исходном разбросе значений 0.09.
Это кандидат в гипотезу, а не закон.

### 4.8 Закон escape по `v4_clean` цел

Все 18 файлов имеют одно сочетание `(acc_every, acc_n, escape_factor) = (250, 2048, 2.0)`.
Escape почти детерминирован при заданном dim: разброс по трём сидам не превышает
одного шага сетки при dim 12–128, тогда как итоговая точность при dim 8 гуляет
от 0.775 до 0.930. Escape и бассейн — разные вещи.

Escape от бюджета не зависит: seg 256, dim 8, одна сетка 250 — при 30k среднее 6333,
при 200k среднее 6417, разница внутри разброса сидов. Это ожидаемо при `lr_decay=False`.

### 4.9 Инвентарь схем

Аудит от 7 августа: 46 JSON в `results/v4` и `results/v4_clean` распадались ровно
на 2 схемы, отличающиеся **только** ключом конфига `world`; `escape_criterion`
= `val_accuracy` и `escape_threshold` = 0.03125 везде. `results/v4_clean/` — 18 файлов,
загрязнения `gate_*` нет. Для dim 8 файлы в `v4` и `v4_clean` **дублируются**
побайтно — при агрегации по каталогам их нельзя считать дважды.

## 6. Открытые вопросы

- Прирост от уменьшения `recency_scale` не проверен на независимом наборе (4.4).
- Почему обучение выбирает наклон больше оптимального по жёсткой точности —
  неизвестно. Гипотеза, не проверенная: цель — перекрёстная энтропия (уверенность),
  а чекпойнт отбирается по мягкой точности (`--select-metric soft` по умолчанию),
  и то и другое может вознаграждать наклон сильнее.
- Несоответствие отбора и отчёта (`select_metric soft` против жёсткого
  `answer_acc`) остаётся во всех сериях.
- Ёмкость при сходимости не измерена: все 15 прогонов развёртки бюджетом ограничены.
- Природа «хорошего бассейна» (0.93 … 0.97 против 0.70 … 0.84) не объяснена.
  Три сида на точку для этого мало.

## 8. Дальнейшие шаги, по приоритету

### 8.0 Зафиксировать текущее состояние (сделать первым, 1 минута)


Во втором `git status` убедиться, что `.pt` не подтянулись (их перекрывает
`.gitignore`), а `recency_ablation.json` подтянулся.

### 8.1 Перепроверить прирост от уменьшения давности на независимом наборе

Одна правка `probe_recency.py`: аргумент смещения сида оценочного мира, сейчас
там жёстко `cfg["seed"] + 100_000`. Добавить `--eval-seed-offset` со значением
по умолчанию `100000`, чтобы поведение не изменилось, и прогнать со смещением,
скажем, `300000`.

Читать: сохраняется ли знак прироста при множителе 0.5 во всех 15 прогонах.
Если да — утверждение 4.4 подтверждено на данных, не участвовавших ни в обучении,
ни в отборе. Если нет — отозвать 4.4 явно.

Важно: при смещённом сиде строка «воспроизведение» перестанет совпадать с JSON,
и это правильно. Сверку надо либо выключать, либо всегда прогонять обе сетки —
базовую для сверки и смещённую для вывода.

Стоимость: минуты, обучения нет.

### 8.2 Двухступенчатое считывание — главный содержательный шаг

Из 4.2 и 4.3 следует конкретное изменение архитектуры. Давность нужна **только**
чтобы различать события с одинаковыми ключами; для этого достаточно разрешать
ничьи, а не наклонять весь спектр скоров. Двухступенчатое считывание: сначала
аргмакс по семантике, затем среди почти равных по семантике выбрать позднейшее.

Ожидание, которое проверяется: спад по дистанции исчезает (как при множителе 0),
а `answer_acc` **не** рушится (в отличие от множителя 0), потому что правило
последней записи сохраняется.

Это проверяется на уже сохранённых весах, без обучения — отдельным скриптом
по образцу `probe_recency.py`. Порог «почти равенства» придётся подобрать;
разумная отправная точка — тот же допуск `1e-6`, что уже используется для
`tie_count` в `model.py:98`, но его надо мерить, а не назначать: при
`score_scale` порядка 40–70 семантические скоры своего слота равны точно,
а чужого — отличаются на конечную величину, и разделяющий зазор надо посмотреть
по данным.

Порядок: сперва измерить распределение зазора между максимумом и вторым
значением по слотам на сохранённых весах, потом выбирать порог, потом
реализовывать ридаут. Не наоборот.

Если проверка на весах подтвердит ожидание — тогда правка `model.py` и обучение
с новым ридаутом, одним изменением.

### 8.3 Ёмкость при сходимости

Все числа в 4.5 — оценки снизу. Чтобы говорить о ёмкости, нужна хотя бы одна
длина, доведённая до плато (`best_epoch` заметно меньше `epochs`). Дешевле всего
взять seg 256 (96.3 ep/s) и дать 1M эпох на 3 сидах: около 3 часов на прогон,
три параллельно — примерно 3.5 часа. Часть данных уже есть: `long_dim8_gpu_s*_e1M`
из v4, но они **без весов и без метрик по слотам**, поэтому для нынешних вопросов
непригодны и их придётся переснять версией v5.

### 8.4 Больше сидов на точку

Лотерея бассейна (4.5) мажет кривую сильнее эффекта длины. Три сида недостаточно
ни для медианы, ни для разговора о бимодальности. Разумный минимум — 8–10 сидов
на одну-две длины при среднем бюджете, а не 3 сида на пяти длинах.
Оценка при seg 256 и 200k эпох: около 35 минут на прогон, по 3 параллельно,
10 сидов — примерно 2 часа.

### 8.5 Убрать несоответствие отбора и отчёта

`--select-metric hard` уравнивает ридаут пробника с тем, которым печатается
`answer_acc`. Флаг уже есть (`analyze_memory.py:353-363`), по умолчанию `soft`.
Сравнить пару серий с `soft` и `hard` при прочих равных — это снимет конфаунд,
который тянется через все серии, и заодно проверит гипотезу из раздела 6
о том, почему наклон переучен.

## 9. Чего не делать

- Не сравнивать сиды по номеру между мирами numpy и gpu — генераторы разные.
- Не сравнивать `escape_epoch` между прогонами с разным `acc_every`.
- Не считать файлы `v4` и `v4_clean` для dim 8 как независимые — они дублируются.
- Не читать столбец `answer` в абляции при множителе 0 — он обрушен по построению.
- Не делать выводов о ёмкости по прогонам, где `best_epoch` близок к `epochs`.
- Не запускать длинную серию, не прогнав ту же конфигурацию на малом бюджете.
