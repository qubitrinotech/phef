## 0. Основные правила работы

Эти правила имеют приоритет над содержательной частью handoff и непроверенными утверждениями из прошлой переписки. Handoff — датированная запись, а не доказательство текущего состояния.

### 0.1. Источник истины

1. Источник истины — только свежий первичный артефакт, присланный пользователем: полный вывод команды, содержимое файла, JSON, лог, checkpoint metadata, Git-вывод или трассировка.
2. Не утверждать по памяти, имени файла, аналогии, старому handoff или собственному предыдущему ответу, что существует файл, checkpoint, JSON, процесс, флаг, конфигурация, commit, remote, GPU job или результат.
3. Ассистент не имеет прямого доступа к локальной машине, shell, Git, GPU, файлам, исходникам и логам. Все команды запускает пользователь. Нельзя писать «я проверил», «я запустил», «GPU свободна» или «run завершился» без вставленного пользователем подтверждения.
4. ТЗ описывает намерение; handoff и журнал — исторический контекст. Любой изменяемый факт перед использованием сверяется командой.
5. Необъяснённое расхождение чисел, конфигураций или артефактов помечается **[НЕИЗВЕСТНО]**. До объяснения на нём не строить следующий эксперимент и не фиксировать его как результат.
6. **Не переносить структуру JSON из формата stdout.** Ошибка этой сессии: структура MFR-JSON была предположена по виду печатного вывода (`real` в корне), фактически условия лежат под `results`. Схему файла подтверждать чтением ключей, а не аналогией с логом.

### 0.2. Маркировка и порядок ответа

Каждое содержательное утверждение маркировать:

- **[ФАКТ]** — прямо подтверждён первичным артефактом
- **[ВЫВОД]** — логически следует из подтверждённых фактов
- **[ГИПОТЕЗА]** — проверяемое объяснение, не установленный факт
- **[НЕИЗВЕСТНО]** — данных недостаточно; нужен минимальный различающий read-only шаг

Порядок ответа: **сверка фактов → вывод → решение → команда**.

Один ответ — один проверяемый шаг. До команды явно указать:

- что именно она проверяет или меняет;
- какой результат ожидается;
- какой признак успеха должен появиться в выводе.

Если данных не хватает, сначала дать минимальную read-only команду. Не предлагать решение на непроверенной предпосылке. Не использовать формулировки «скорее всего», «обычно», «должно работать» для фактических вопросов о проекте.

**Предрегистрация различающего критерия.** Практика, доказавшая ценность в этой сессии: до запуска измерения записать численные предсказания каждой гипотезы. Критерий для B был сформулирован как «`semantic_inversion_rate` растёт с 8.15 % до ≈13 %», фактически получено 12.45 %. Предрегистрация исключает подгонку интерпретации под результат.

Любое write-действие возможно только после явного подтверждения пользователя. К таким действиям относятся:

После write-действия запросить read-only проверку фактического результата. Не считать действие успешным только потому, что команда была предложена или запущена.

### 0.4. Git discipline

1. Никогда не использовать `git add .`, `git add -A`, массовый commit или массовое удаление без отдельной инвентаризации и явного согласия.
2. Перед commit показывать exact staged file list, `git diff --cached --stat`, `git diff --cached --check` и содержательный staged diff/summary.
3. Использовать явный whitelist путей.
4. `.pt` weights/checkpoints, `logs/`, drafts, backups и неизвестные файлы не добавлять автоматически.
5. Один commit — одна законченная мысль.
6. `git push` — отдельное подтверждаемое действие после проверки remote URL, branch/upstream, точного диапазона `origin/main..HEAD` и состава commits.
7. После push проверять синхронность `HEAD` и `origin/main` через `git status -sb`, `git rev-parse --short HEAD`, `git rev-parse --short origin/main`.

### 0.5. Экспериментальная дисциплина

1. Конфигурацию конкретного train/eval подтверждать полем `config` соответствующего целевого JSON, а не именем файла, старым handoff или пересказом. **MFR-JSON содержит полный `config`** — использовать его.
2. Не переносить без отдельного измерения между разными checkpoint, epoch, seed, `S`, `n_keys`, `rw`, lr, batch size, eval batch size, числа episodes или другого protocol: качество; capacity; устойчивость по seed; peak VRAM; throughput/время; поведение loss; надёжность controls.
3. Для full independent PHEF eval operational PASS определяется только так:

```text
hard_eval = true
real.answer_acc >= 0.90
real.retrieval_acc >= 0.90
shuffled.answer_acc < 0.03125
masked.answer_acc < 0.03125
episodes = 16384 в real, shuffled и masked
```

При `n_values=64`:

```text
answer chance = 1 / 64 = 0.015625
control threshold = 2 × chance = 0.03125
```

4. Distance probes на 1024 episodes — screening/profiling. Они не заменяют full independent PASS.
5. Если checkpoint snapshots отсутствуют между двумя measured epochs, нельзя заявлять более точный historical epoch boundary; новый rerun с более частым сохранением — отдельный эксперимент, а не восстановление старой trajectory.
6. **MFR — механическая диагностика, а не PASS-критерий.** Результаты MFR объясняют механизм, но не заменяют full independent hard-eval и не могут использоваться для заявления PASS/FAIL. Поле `hard_eval: true` в MFR-JSON относится к режиму argmax, а не к operational-протоколу.
7. **Одинаковый `--seed` даёт попарное сравнение.** Проверено: `dup_count` и `tail_distance` совпадают между прогонами до последнего знака. Это радикально повышает чувствительность к разнице между checkpoints — использовать всегда при сравнении весов на одном протоколе.

1. Перед CUDA job read-only проверить активные train/eval processes, GPU compute processes и отсутствие conflict output paths.
2. На единственной GPU не запускать параллельные CUDA jobs.
3. Для CUDA Python использовать:

```bash

```

4. Для PHEF использовать единственный подтверждённый interpreter:

5. Долгие tasks запускать только после подтверждения через `setsid nohup ... < /dev/null & disown`.
6. Не запускать evaluator через pipe с `tail`. **Уточнение:** `| tail -n 40` полностью подавляет вывод до завершения процесса, включая start-строку. Это не сбой, но диагностику приходится вести из второго терминала.

## 3. Механическая модель задачи

Раздел перенесён из предыдущего handoff без изменений: он выведен из фактического исходного кода и новыми данными не опровергнут, а подтверждён.

### 3.1. Определение задачи

**[ФАКТ]** `phef/world.py`, класс `BranchingWorld`:

```python
match = slots == query_slots[:, None]
answer_positions = self.n_segments - 1 - np.argmax(match[:, ::-1], axis=1)
answers = values[rows, answer_positions]
```

**[ФАКТ]** Задача: найти **последнее** вхождение запрошенного ключа в эпизоде длиной `n_segments`. `codebook` пересэмплируется каждый батч и L2-нормируется, поэтому lookup-таблица структурно невозможна. `values` случайны и независимы. `timestamps` — просто `arange(n_segments)`.

**[ФАКТ]** `_sample_slots` реализует overwrite-цепочки через pointer doubling; `reuse[:, 0] = False`; замерено ускорение 551.6 → 23.1 мс при bs=8, n_segments=131072.

### 3.2. Формула адресации

**[ФАКТ]** `phef/model.py`, `PHEF.forward`:

```python
query_state = self.query_encoder(query_keys)
memory_keys = self.key_encoder(codebook)
semantic = torch.gather(
    torch.einsum("bd,bkd->bk", query_state, memory_keys) / math.sqrt(self.dim),
    1, slots)
recency = timestamps.float() / max(1, self.n_segments - 1)
scores = self.score_scale * semantic
scores = scores + self.recency_scale * recency
```

То есть:

\[
s_j = \alpha \cdot \frac{\langle q,\; k_{\mathrm{slot}_j}\rangle}{\sqrt{d}} + \beta \cdot \frac{t_j}{S-1},
\]

где \(\alpha =\) `score_scale`, \(\beta =\) `recency_scale`, \(d =\) `dim`, \(S =\) `n_segments`, \(t_j = j\).

**[ФАКТ]** При `hard=True` берётся строгий `argmax`, `last_tie_rate` считается по порогу `1e-6`. Softmax-режим используется только при обучении. Далее `gate = sigmoid(memory_gate)`, `hidden = norm(query_state + gate * memory_state)`, `logits = head(hidden)`.

**[ФАКТ]** `phef/memory.py` содержит класс `EventMemory` с `rerank`-механизмом, но `PHEF.forward` его **не использует**. Это неиспользуемый в текущем пути код.

### 3.3. Центральное следствие

**[ВЫВОД]** Все вхождения одного и того же slot имеют **одинаковый** semantic-score, потому что `semantic` есть `gather` по `slots` из матрицы, индексируемой ключом, а не позицией. Следовательно, различить дубликаты одного ключа может **только** recency-слагаемое.

**[ВЫВОД]** Правильное решение факторизуется на две независимые подзадачи:

1. **семантическое различение** — отделить правильный ключ от остальных `n_keys - 1` ключей;
2. **recency-выбор** — среди `dup_count` вхождений правильного ключа выбрать самое позднее.

**[ВЫВОД]** Ошибки строго делятся на два **несовместимых** класса:

```text
same_key_recency_error   : slots[pred] == query_slot, но pred != answer_position
wrong_key_semantic_error : slots[pred] != query_slot
```

Третьего варианта не существует. Это делает диагноз однозначным.

**[ФАКТ]** Разложение подтверждено численно: `margin_nonpositive_rate` точно равен `wrong_key_semantic_rate` (0.083984 на epoch 750, 0.132324 на epoch 1500). Каждая ошибка адреса — в точности неположительный margin.

### 3.4. Условие корректности и recency budget

**[ВЫВОД]** Правильная позиция \(P\) побеждает конкурента \(j\), если

\[
\alpha\,(\mathrm{sem}_P - \mathrm{sem}_j) > \beta \cdot \frac{t_j - t_P}{S-1}.
\]

Для конкурентов с **другим** ключом определяем семантический зазор

\[
\Delta_{\mathrm{sem}} = \min_{j:\ \mathrm{slot}_j \neq \mathrm{query\_slot}} (\mathrm{sem}_P - \mathrm{sem}_j).
\]

Отсюда **recency budget**:

\[
B = \frac{\alpha\,\Delta_{\mathrm{sem}}\,(S-1)}{|\beta|}
\quad[\text{timestamp-шаги}],
\qquad
B_{\mathrm{norm}} = \frac{B}{S-1} = \frac{\alpha\,\Delta_{\mathrm{sem}}}{|\beta|}
\quad[\text{безразмерная}].
\]

**Интерпретация:** \(B\) — максимальное число timestamp-шагов, на которое recency способна перебить семантику. Если \(B_{\mathrm{norm}} > 1\), recency не может перебить семантику ни на какой дистанции внутри эпизода.

**[ВЫВОД]** Порог семантической безопасности на всём эпизоде:

\[
\Delta_{\mathrm{sem}} > \frac{|\beta|}{\alpha}.
\]

**[ВЫВОД]** \(\Delta_{\mathrm{sem}}\) может быть **отрицательным** — семантическая инверсия, при которой правильный ключ проигрывает чужому ДО учёта recency, и никакая recency его не спасёт. Такие эпизоды не являются «бюджетом» и учитываются отдельно как `semantic_inversion`.

### 3.5. Конкурирующие требования

**[ВЫВОД]** Модель обязана одновременно держать \(\beta\) достаточно большим для решения recency-подзадачи и \(\alpha\Delta_{\mathrm{sem}}\) достаточно большим, чтобы recency не перебивала семантику на больших дистанциях.

**[ВЫВОД]** Измерения этой сессии показали, что на замеренном отрезке этот конфликт **не является** лимитирующим: \(B_{\mathrm{norm}}\) остаётся 2.2 при пороге 1.0, а `same_key_recency_error = 0`. Лимитирующим оказалось само \(\Delta_{\mathrm{sem}}\).

### 3.6. Почему \(\Delta_{\mathrm{sem}}\) хрупок: усиление через минимум

**[ВЫВОД]** \(\Delta_{\mathrm{sem}}\) есть **минимум** разности по \(n_{\mathrm{keys}} - 1\) конкурентам. Минимум по выборке из 131 071 элемента чрезвычайно чувствителен к малым изменениям формы распределения: сдвиг геометрии представлений на проценты перестраивает именно экстремум, оставляя центр почти нетронутым.

**[ФАКТ]** Наблюдаемое усиление: все \(\lVert\Delta W\rVert/\lVert W\rVert\) лежат в диапазоне 0.0024…0.0697, mean \(\Delta_{\mathrm{sem}}\) упал на 8.8 %, а число инверсий выросло на 52.7 %.

**[ВЫВОД]** Это объясняет, почему `sel_acc = 1.0` не предсказывает дальнюю capacity. При training-режиме `n_keys = 512` минимум берётся по 511 конкурентам; при `K = 131072` — по 131 071. Хвост распределения минимума растёт с числом конкурентов, и деградация формы проявляется только там. Внутренний probe структурно слеп к этому.

## 7. Механизм установлен: semantic collapse

Это главный содержательный результат сессии.

### 7.1. Предрегистрированные гипотезы

**[ГИПОТЕЗА A] Recency drift** — Phase B смещает баланс в пользу recency-эвристики. Предсказание: рост `same_key_recency_rate`, падение \(B_{\mathrm{norm}}\) ниже 1, рост \(|\beta|/\alpha\).

**[ГИПОТЕЗА A′] Порогово-чувствительный drift** — уточнение после замера скаляров: модель работает при \(B_{\mathrm{norm}} \approx 1\), и 2 % сдвига `thr` перебрасывают эпизоды через порог. Требует \(\Delta_{\mathrm{sem}} \approx 0.70\). Предсказание: `semantic_lead_rate` остаётся ≈0.918, разрыв `lead − retrieval` растёт до ≈0.05.

**[ГИПОТЕЗА B] Semantic collapse** — деградирует семантическая разделимость ключей. Предсказание: `semantic_inversion_rate` растёт с 8.15 % до ≈13 % при `B_norm_mean` около 2.2.

## 9. CAMP: цель conservation-loss определена данными

**[ГИПОТЕЗА]** Conservation-Aware Memory Plasticity: Phase B должен адаптироваться к длинному \(S\), не разрушая механизм дальней адресуемости.

Замысел: anchor-набор синтетических эпизодов с детерминированными seeds, не используемых для task loss, даёт эталонные сигнатуры на checkpoint с подтверждённо высокой capacity. Phase B получает дополнительный loss, охраняющий эти сигнатуры.

### 9.1. Что отвергнуто измерением

**[ВЫВОД]** \(B_{\mathrm{norm}}\) **как цель отвергнут.** Он равен 2.20 при пороге 1.0 и сжался всего на 4.1 % при падении точности на 4.8 п.п. Охранять его — охранять не лимитирующий параметр.

**[ВЫВОД]** Отношение α/\|β\| **отвергнуто.** Сдвиг 4.74 % за 1750 epoch, канал `same_key_recency` пуст. Ограничение ничего не предотвратило бы.

**[ВЫВОД]** L2 к anchor-весам **отвергнут.** Все \(\lVert\Delta W\rVert/\lVert W\rVert\) в диапазоне 0.0024…0.0697, при функциональном сдвиге на 2.7σ. Ограничение весов не поймало бы деградацию.

**[ВЫВОД]** Среднее \(\Delta_{\mathrm{sem}}\) **отвергнуто как цель.** Оно упало лишь на 8.8 %, пока инверсии выросли на 52.7 %.

### 9.2. Что данные оставляют

**[ВЫВОД]** Целью должен быть **per-episode \(\Delta_{\mathrm{sem}}\), ограниченный снизу**, с акцентом на нижние квантили, либо непосредственно доля эпизодов с \(\Delta_{\mathrm{sem}} \le 0\).

Форма из исходного замысла подходит структурно:

\[
\mathcal L_{\mathrm{margin}} = \frac1N\sum_i \left[\max\left(0,\; m_i^\star - \delta - m_i\right)\right]^2,
\]

но \(m_i^\star\) обязан быть **per-episode** anchor-значением зазора, а не агрегатом.

**[ВЫВОД]** Anchor-эпизоды должны генерироваться при **высоком** `n_keys`, а не при training-значении 512. При 512 семантических инверсий нет, и anchor не содержал бы сигнала о том, что рушится. Это прямое следствие §3.6.

**[ВЫВОД]** Целевая мода для охраны идентифицирована: бин \(\Delta_{\mathrm{sem}} \in [-0.1, -0.01)\), выросший с 130 до 185 эпизодов, и бин \([-1, -0.1)\), выросший с 10 до 28.

**[ВЫВОД]** Любой CAMP-эксперимент требует baseline с идентичной конфигурацией и тем же `--seed`. Без парного baseline результат не является причинным.

**[НЕИЗВЕСТНО]** Ничего из CAMP не реализовано. Это замысел, не код.

## 10. Algorithmic Density: отложенный раздел

Раздел записан по просьбе пользователя как материал для размышления. **Вся содержательная часть имеет статус [ГИПОТЕЗА]**, кроме явно помеченных фактов. Внешние численные оценки в проекте не верифицированы и не могут обосновывать эксперимент по §0.1.

### 10.1. Подтверждённое основание

**[ФАКТ]** 58 179 параметров, 232 716 байт в fp32, 58 179 байт в int8 (§5).

**[ФАКТ]** Эта модель адресует \(2^{22} = 4194304\) ключей с `real answer = 0.978455`, `real retrieval = 0.978271`, controls 0.014038 / 0.016296, 16384 episodes (§8.1).

**[ФАКТ]** `keys_per_param` при \(2^{22}\) = 72.0931; при \(2^{23}\) было бы 144.1862.

**[ФАКТ]** Обучение шло при `n_keys = 512`; eval прошёл при 4194304. Отношение \(4194304/512 = 8192\).

**[ФАКТ]** `codebook` пересэмплируется каждый батч и L2-нормируется, поэтому lookup-таблица структурно невозможна (§3.1).

**[ВЫВОД]** Значит параметры кодируют не знание, а **процедуру** связывания, адресации и выбора последнего вхождения. Эта процедура работает на числе ключей, в 8192 раза превышающем training-режим. Это единственный аргумент, несущий вес в утверждении «не жульничество», и он опирается на подтверждённый факт о codebook.

### 10.2. Предложенные метрики

**[ГИПОТЕЗА]** Algorithmic density:

\[
\rho_{\mathrm{alg}} = \frac{\log_2 K \cdot \mathrm{acc}}{N_{\mathrm{params}}}.
\]

**[ГИПОТЕЗА]** Generalization ratio:

\[
G = \frac{K_{\mathrm{eval}}}{K_{\mathrm{train}}} = \frac{4194304}{512} = 8192.
\]

**[ГИПОТЕЗА]** \(G\) измеряет, во сколько раз механизм переносится за пределы режима обучения. Для параметрической памяти \(G \approx 1\) по определению.

**Внешние оценки, не верифицированные в проекте:** ёмкость трансформеров ≈3.6 бита на параметр (bfloat16 3.51 → float32 3.83); независимая оценка 2 бита на параметр, сохраняющаяся при int8; сравнение с ≈1.19 млрд параметров при 3.6 бит/параметр. Эти числа взяты из внешней литературы, в репозитории не проверялись и служат только ориентиром.

### 10.3. Три направления

**[ГИПОТЕЗА] Hypernetwork-генерация специалистов.** Гиперсеть \(H_\phi\) по дескриптору режима (`n_keys`, `S`, `overwrite_p`) генерирует \(\theta = H_\phi(e)\) — весь PHEF целиком. Вместо одного компромиссного checkpoint получается континуум специалистов, каждый оптимальный для своего \(K\), с возможностью интерполяции на невиданные \(K\). Прямо атакует проблему Phase B: вместо разрушения раннего механизма адаптацией — семейство механизмов, индексированное режимом. Внешний ориентир (не верифицирован): HyperCompress кодирует параметры CNN в 128-байтовый латентный код.

**[ГИПОТЕЗА, МОТИВИРОВКА ИСПРАВЛЕНА] Параметризация β через \(\hat\Delta\).** Вместо свободных α и β задать

\[
\beta = \frac{\alpha \cdot \hat\Delta}{\max(1, B_{\mathrm{target}})},
\]

где \(\hat\Delta\) — EMA измеренного \(\Delta_{\mathrm{sem}}\). Добавляет ноль параметров, не требует replay-буфера.

**[ВЫВОД]** Исходная мотивировка «оптимизатор может разбалансировать α и β» измерением **не подтверждается**: отношение сдвинулось на 4.74 % за 1750 epoch, `same_key_recency_error = 0` на обоих checkpoints. Идея остаётся ценной как архитектурная гарантия, но она **превентивная, а не корректирующая** — она закрывает канал отказа, который в замеренных данных практически не открыт, и не объясняет \(\Delta\text{answer} = -0.04779\).

**[ГИПОТЕЗА] Int8-развёртывание.** Решение принимается через argmax разностей, критично лишь сохранение знака \(m = s_P - \max_{j \ne P} s_j\).

**[ФАКТ, УСИЛИВАЮЩИЙ ГИПОТЕЗУ]** `semantic_true.mean = −9.31` при `margin.mean = 0.2250` и `semantic_true.std = 3.76`. Модель работает исключительно на разностях, абсолютный уровень скоров велик и не важен. Релевантный масштаб для шума квантизации — margin порядка 0.16–0.22, а не абсолютные −9.31.

**[ВЫВОД]** Это проверяемо существующим MFR без новой архитектуры: прогнать int8-версию на том же `--seed` и сравнить `margin_nonpositive_rate`, гистограмму `margin` и `error_decomposition`. Критерий: сохранение знака margin в тех же эпизодах. MFR остаётся механической диагностикой, PASS по нему не устанавливается.

**[ВЫВОД]** Из трёх направлений int8-проверка — единственное, не требующее нового архитектурного кода.

3. **Независимый 8M hard-eval Early KD32** через `eval_recall_checkpoint.py`, 16384 episodes, полный протокол PASS — без изменений в коде.
4. **Геометрия `key_encoder`** — закрыть открытые вопросы 6 и 7. Требует нового скрипта, то есть write-действия.
5. **Int8-проверка через MFR** — прогон квантизованной версии на том же `--seed`, сравнение `margin` и `error_decomposition`.
6. **Только затем CAMP** с явным парным baseline, per-episode \(\Delta_{\mathrm{sem}}\)-anchor при высоком `n_keys`.

**[ВЫВОД]** Шаг 1 приоритетен: он единственный даёт эталонные значения для проектирования conservation-loss. Без anchor от работающего механизма CAMP проектируется вслепую.

**Read-only preflight перед шагом 1** — блок §1, затем пробный батч с `--batches 1 --conditions real` и внешним VRAM-семплером по §0.6 п.8.
